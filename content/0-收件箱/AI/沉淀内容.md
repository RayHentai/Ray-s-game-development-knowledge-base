## 错点、卡点清单

### 项目

#### 本轮(程序化网格生成)错点清单: √

1. **顶点坐标空间**:错答 "顶点存世界坐标" → 正:顶点存**本地坐标**,Transform 才负责变换到世界空间。
2. **triangles 存什么**:错答 "存顶点坐标" → 正:triangles 是 int 数组,存的是**顶点在 vertices 数组里的索引(下标)**,靠下标去取 Vector3。
3. **绕序反了的现象**:错答 "变黑" → 正:**背面剔除**,那一面根本不渲染,看到的是**穿透**(看穿到背后),不是变黑。
4. **`sharedMesh` 是什么**:错猜 "跟着色相关" → 正:与着色无关,`shared` 指**共享同一个网格原件**;`mesh` 给专属拷贝(改它不连累别人)、`sharedMesh` 碰原件(改它所有共用者一起变、还会改到 Prefab 资源)。

#### 本轮(sin/cos 圆柱展开)错点清单: √

5. **一圈顶点坐标**:初答卡在"弧长算 xy"(弧长给不了坐标)→ 正:相邻顶点夹角 `2π/n`,第 i 个顶点转过 `θ = i × 2π/n`,坐标 `x = sin θ · r`、`y = cos θ · r`(角度→坐标靠三角函数,从直角三角形邻边/对边推)。
6. **`Mathf.Sin`/`Cos` 单位**:要**弧度**不是角度;塞 `Mathf.Sin(90)` 会当 90 弧度算;手里是角度先 `× Mathf.Deg2Rad` 转弧度。

7. （不列为错点、列为**直觉待建**)弧度制没成直觉——心里的圆用 360° 搭、弧度靠临时转换。这条不是"抄一句就好"的错点,是要专项重建的,单独标着。

#### 本轮(无限地图拼接)错点 / 缺口清单:

1. **新块起点坐标取法**:闭卷调不出 → 正:**混合取法**——**z** 接着旧块末尾往前(防重叠 + 续延伸),**xy** 取旧块末尾那圈(接缝横向/高度对齐,防断层)。三方向要求不同,故不取同一点。
2. **Lerp 首尾衔接的目的**:此前只知"用了 Lerp"→ 正:接缝硬接会有急转/断层,故接缝后**若干圈用 Lerp 从旧块末尾高度渐变到新块本高度**,平滑过渡。

3. （讲对了、记为正例)"凹凸导致接缝贴图/高度对不齐"这个**问题意识**你主动讲出来了——对齐的必要性你懂,只是没推到"y 取末尾"这个解法。问题端在,解法端待补。

#### 本轮(z 衔接)错点清单：

1. **新块首圈 z 衔接**:反复错答"= 旧块末圈 z(相等)"→ 正:**= 旧块末圈 z + 一个圈间隔**。相等会导致两圈落在同一 z、重叠;差一个间隔才与块内圈距一致、严丝合缝接上。**"接续 ≠ 相等,差一个步长"**——这个直觉很顽固,记死。
2. **countZ 语义**:错认"countZ = 圈数"→ 正:**countZ = 间隔数,实际圈数 = countZ + 1**(fencepost / 栅栏柱关系)。末圈 z 因此 = countZ(不是 countZ−1)。

#### 程序化网格生成 闭卷的错点/卡点清单: √

真错点(概念层,要记):

1. **四角偏移方位**:错答"右下=current+(countX+1)、左上=current+1"→ 正:**右下=current+1(同圈右邻)、左上=current+(countX+1)(前一圈同角度)**。`+1`管同圈(下排)、`+(countX+1)`管跨圈(上排);错在"上下"(哪一圈)不在"左右",且与顺逆时针无关。
2. **格子 fencepost**:顶点方向 countX+1/countZ+1,但**格子方向是 countX/countZ**(n桩夹n-1段),循环用 `< countX`/`< countZ`、数组 `countX*countZ*6`。

卡点/注意事项(非概念错,记着提醒自己):  
3. **countX/countZ 高频手误**:今天 X/Z 混淆出现 3+ 次(循环边界、current 系数敲成 countZ+1)。命名太像导致的手误,非知识问题。对策:写完扫一遍每个 count 对不对,或起更区分的名。

4. **循环三段一致**:内层 `for(x...; x<=countX; z++)` 把自增写成 `z++`——for 的初始/判断/自增必须同一变量。

**`++i` vs `i++` 什么时候有区别**:嵌在表达式里(如 `arr[i++]` 当下标)→ 有区别,后增才先用当前值、前增会先加导致跳位/越界;单独成句(`i++;`)→ 无区别,等价。选择依据是"有没有嵌在表达式里",不是笼统的性能。(附:"++i性能更好"对 C# int 不成立,那是 C++ 重迭代器的事。)

### CSharp

#### 委托事件 错点 / 缺口清单 √

**新知点(非错点，首次补上）**
- 事件内存泄漏 / lapsed listener：事件订阅列表持有订阅者引用 → 未 -= 则 GC 回收不掉 → 该死不死。
	Unity 铁律：OnEnable += / OnDisable(OnDestroy) -=，成对，谁订阅谁退订。
- 内存泄漏 ≠ 崩溃。泄漏 = 该回收的内存没回收、持续占用（一种状态）；
  崩溃(OOM)只是泄漏累积到耗尽内存时的“可能”后果，非必然、非最常见。
  典型表现更多是：内存走高、越用越卡、掉帧、系统杀后台（尤其移动端）。
- 事件泄漏危害两条腿：
	- ①占内存（可能累积到崩）
	- ②僵尸对象被继续调用（逻辑bug，与内存涨不涨无关）。

#### 协程 错点 / 缺口清单 √

**新知点/易混点**
- yield return 后面的值，Unity 按【类型】决定等待策略：
  - YieldInstruction 子类(WaitForSeconds/WaitForFixedUpdate/WaitForEndOfFrame)→ 按各自规则
  - IEnumerator(嵌套协程)→ 等子协程结束
  - null → 等下一帧
  - 其他任意类型(如 int 0)→ Unity 不识别，降级当 null 处理，也等一帧
- 故 yield return 0 与 yield return null 表现相同(0 被当 null)，但语义上应写 null；
  写 0 会误导读者以为“等0秒”。行为无差，可读性有差。

**易错/坑**
- 协程生命绑在所在 MonoBehaviour：GameObject 被 Destroy / 组件 SetActive(false) → 协程【静默停止】，
  没跑完的逻辑(如“等5秒存档”)悄悄不执行、不报错。典型坑：以为会执行的延迟逻辑没发生。
  ⚠ 与事件内存泄漏【方向相反】：事件是“该停不停、赖着泄漏”；协程是“没料到就停”。不同源，勿混。
  为什么协程不泄漏：Unity 自己调度管理，对象销毁时一并清理，不存在外部长命列表持引用。
- StopCoroutine 必须和 StartCoroutine 配对：
  - 字符串启动 → 可字符串停；但有反射开销、不能传复杂参数
  - 方法/IEnumerator 启动 → 想停必须存下 IEnumerator/Coroutine 引用，用引用停
  - 陷阱：StartCoroutine(Foo()) 启动后用 StopCoroutine(Foo()) 停不掉(生成了新的 IEnumerator，非同一个)
- 协程在主线程：某一步重计算会卡死那一帧。协程只能“分帧”不能“分线程”，重活需真多线程/Job System。

#### 值类型 vs 引用类型 错点 / 缺口清单 √

核心图（钉死）
- 变量/格子(栈) vs 对象(堆)：变量是“存东西的格子”，对象是 new 出来的实体。
  - 值类型格子里装【数据本身】；引用类型格子里装【地址】，地址指向堆上的对象。
- 只有 new 在堆上造对象；赋值(=)从不造对象，只抄格子内容(值→抄数据，引用→抄地址)。
  数“堆上有几个对象”= 数执行了几次 new。
- 存储位置由“变量寄居在哪”决定，不由“是不是值类型”决定：
  - 局部变量 → 栈；对象的字段 / 数组元素 → 跟着对象在堆(值类型字段也在堆)。
  - “值类型=栈”是不准确的流行说法。

传参（默认都是“值传递”＝传格子内容的拷贝）
- Change(a) 传的是 a 格子内容的【拷贝】到新格子 x，x≠a，是两个格子。
  值类型：拷贝数据；引用类型：拷贝地址(两格子指向同一对象)。
- 顺着地址改对象(x.level=99) → 外面看得到(同一个对象)。
- 改副本格子自己指向哪(x=new…) → 只动 x，不动 a → 外面看不到。
- 一句话：顺地址改对象=外部可见；改副本格子的指向=外部不可见。

生命周期 / 释放
- 栈：出作用域【立即、自动、零成本】释放(栈帧弹出)，不需要 GC。值类型局部变量、引用变量本身都在此列。
- 堆：对象在“无任何引用指向它”后成为垃圾，等 GC 在【不确定时机】回收。非确定性。
- 后果(埋点)：new 得勤→垃圾多→GC 勤→卡顿(GC尖峰)。优化方向：减少堆分配、别在 Update 里频繁 new。

#### 装箱/拆箱 错点 / 缺口清单 √

**装箱/拆箱**
- 装箱：值类型 → object。堆上新开空间，把值【拷贝】进去，引用变量存该堆对象地址。
  拆箱：object → 值类型，把堆里的值【拷贝】回栈上值类型变量，必须显式强转。两次都是拷贝。
- 关键：装箱是拷贝、两份独立。 object o = i; 之后改 i，o 不变(o 指向堆里那份独立拷贝)。
- 箱子类型焊死：object o = 10 里箱子永远是 int。o="10" 是 o 改指新对象，不是箱子内容变类型。
  拆箱必须按装入时的确切类型拆：(int)o 对，(double)o 崩(InvalidCastException)。
  拆箱的 (int) 是“报对暗号原样取回”，不做数值转换，别和 (int)10.5 那种数值强转混。
- 性能开销的根子：不是“转换”动作，是【堆分配 + GC 压力】。装箱是【隐蔽的堆分配】(没写 new 却 new 了)。
  循环/Update 里频繁装箱 → 大量小垃圾 → GC 频繁 → 卡顿。

**泛型 ↔ 装箱**
- 无泛型年代：ArrayList 内部用 object 存 → 存取值类型必装拆箱(存一万 int = 装箱一万次)。
- List\<int> 编译期锁定 int，直接按 int 存取，全程不碰 object，不装不拆。
- 泛型价值：
	- ①避免装拆箱(性能) 
	- ②编译期类型安全(塞错类型直接编译报错，不像 ArrayList 到运行时才崩)。

#### 容器 错点 / 缺口清单 √

**List**\<T> **底层与成本**
- 底层 = 数组(连续内存)。有初始容量，满了扩容，一般翻倍。
- 扩容真实动作 = 新开2倍数组 + 旧元素全量拷贝 + 旧数组丢弃(等GC)。不是原地续。
  已知规模就 new List\<T>(容量) 预设，避免反复扩容拷贝。
- 成本地图：
  - 按下标 list\[i]：O(1)，与 i 大小无关(算地址直达，不遍历)。
  - 末尾 Add(不扩容)：O(1)，前面不动；触发扩容那一次 O(n)(新数组+拷贝)，平摊仍近 O(1)。
  - 中间/开头 插入或删除：O(n)，要移动插入点之后所有元素。
  - 按值查找 Contains/IndexOf：O(n)，遍历。

**Dictionary<TKey,TValue> 底层**
- 底层 = 哈希表。key 经哈希函数算出哈希值 → 直接映射到数组下标 → value 存/取“算出位置直达”，不遍历。
- 故按 key 查找 = O(1)。哈希冲突(不同key同下标)内部有机制处理(如挂链)，先记主干。

**选择依据**
- 要“按下标取第N个 / 按顺序遍历” → List。
- 要“拿 key 查对应 value” → Dictionary。
- 增删：List 末尾快(O(1))、中间/开头 O(n)；Dictionary 按 key 增删都 O(1)。

**易混点（自己的混淆，记牢）**
- “下标访问”≠“按值查找”：list\[5] 是 O(1)(算地址直达)，Contains(x)/IndexOf(x) 才是 O(n)(遍历)。
  闭卷时一度把两者混了，误以为 list\[5] 要遍历 → 一提即回。

#### 类型转换 错点 / 缺口清单 √

**is / as / 强转 (Type)**
- is：判断变量是不是某类型，返回 bool。 if (obj is Player) → true/false。
- as：引用类型/可空类型转换，“当成目标类型试试”。
  失败【不抛异常，返回 null】。 Player p = obj as Player;  失败 p\==null。
- (Type) 强转：失败【抛异常 InvalidCastException，程序崩】。
	- ①有继承关系的向下转型(父转子) 
	- ②值类型数值转换 (int)3.14。
- 分水岭(核心)：强转失败=崩；as 失败=给 null。
  确定能转、转不了是bug该暴露 → 强转；不确定、失败是正常、不想崩 → as + 判 null。

**模式匹配（现代C#，首选）**
```CSHARP
if (obj is Player p) {}
```

- 判类型 + 是则转好赋给 p，一步到位，只查一次类型。

**“安全转、失败别崩”标准写法**
- 写法A： 
```csharp
Player p = obj as Player; 
if (p != null) { //用p }
```

- 写法B(更简)： 
```csharp
if (obj is Player p) { //用p }
```

- 反例：转换结果没接住(丢了)，且查了两次类型。
```csharp
//先 
if(obj is Player) 
//再 
obj as Player 
```

  要点：转换结果必须用变量接住；判断+转换能合并成 is Type 变量。

#### 属性 错点 / 缺口清单 √

**属性 property**
- **本质：** 属性 = **伪装成字段的方法**。 obj.Hp = 100 外表像给字段赋值，实际调用 set 方法；读调 get。
  外表像字段(直接读写)，内里是方法(能塞逻辑)。
- 价值(字段做不到的)：get/set 是方法能插代码 → 
	- ①校验(set 拦非法值) 
	- ②只读/只写控制 
	- ③读写附带逻辑。
  set 里的 value = 关键字，代表外部赋进来的值。
- **自动属性：** 不需要任何额外逻辑时的偷懒写法，编译器自动生成隐藏字段+标准getset。

```csharp
public int Level
{ 
	get; 
	set;
}  
```

  ⚠ 一旦 set 需要逻辑(校验/钳制/附带动作) → 不能用自动属性，必须展开成带字段的完整属性。
- 只读/受控写：

```csharp
//外部只读
public int Level => level;  
//或  
public int Level
{ 
	get; 
}  

//外部只读、类内部可写
public int Level
{   
	get; 
    private set; 
}
```

- set 里钳制的标准套路：先把 value 修正到合法范围，最后统一 字段 = value 落库。
  ⚠ 易错：分支里改的必须是 value(入参)，不是字段；否则最后 字段=value 会覆盖掉钳制。

```csharp
private int i = 0;
public int I
{
	get { return i; }
	private set
	{
		if (value < 0)
			value = 0;
		i = value;
	}
}
```

**Unity 实践**
- `[SerializeField]` private int hp;  优于  public int hp;
  - public：Inspector 可调，但任何脚本也能乱改(破坏封装)。
  - `[SerializeField]` private：Inspector 可调 + 保持 private(别的脚本改不了)。规范做法。
  - 破除误解：字段要在 Inspector 显示【不必】public，`[SerializeField]` 让 private 也能序列化。

#### 接口 vs 抽象类 错点 / 缺口清单 √

**接口 vs 抽象类**
- 接口 interface：能力契约，只声明“必须有哪些方法/属性”，传统接口无实现、无实例字段。
- 抽象类 abstract class：不能实例化的父类，可有现成实现+字段，也可留 abstract 方法强制子类实现。
- 关键区别：
  ①有无实现：抽象类能(子类共用)；传统接口只声明。
  ②有无字段：抽象类能存实例字段；接口不能。
  ③继承数量【最硬】：一个类只能继承 1 个抽象类(单继承)，但能实现多个接口。
- 选择判据：
  - 抽象类 = **“是什么，描述对象”**(is-a)：一组类共享本质+共用代码。Player/Enemy/Boss 都是角色，共享hp和受伤逻辑 → 抽象类。
  - 接口 = **“能做什么，描述行为”**(can-do)：给本质不同的类赋予同一能力。Player/炮塔/陷阱 本质不同但都“能被攻击” → 接口 IAttackable。
- 常态：一个类既继承一个抽象类、又实现多个接口。 

```csharp
class Player : Character, IAttackable, IMovable。
```

  抽象类管本质+共用实现(唯一)，接口管可叠加的能力(多个)。
- Unity 场景：UI 事件接口如 IPointerClickHandler(实现 OnPointerClick)→ 赋予“能被点击”能力。命名惯例：接口以 I 开头(IList/IDictionary 也是)。

#### 三步法 class vs struct √

class vs struct（用三步法学的样板）
- 锚(例子)：
	- Player(有hp有行为、要被多处引用) = class；
	- Position(纯x/y/z数据、大量创建拷贝) = struct。
- 从锚推出的区别（都从"纯数据拷贝 vs 有身份共享"推，非背）：
  ① 值/引用：
	- 纯数据适合拷贝一整份→值类型(struct)；
	- 要被共享的实体适合传地址→引用类型(class)。
  ② 赋值行为：
	- class b=a 改b连带改a(同一对象)；
	- struct p2=p1 改p2不影响p1(两份独立数据)。
  ③ null：
	- class 可为 null(攥地址、可空着)；
	- struct 不能为 null(直接就是数据本身)。
  ④ 默认值：
	- 都有——值类型字段→默认值(0)，
	- 引用类型字段→null。
	- struct 全默认值如 Position=(0,0,0)。
  ⑤ 构造约束：
	- struct 不能自己写无参构造(老规则)；写了【带参构造】则必须给所有字段显式赋值；
	- class 无此限制(漏赋的自动默认/null)。
- ⚠ 易滑点(归因，重点盯)：struct 自定义构造必须赋全，【不是】因为"写了构造→字段初始化机制失效"，
  【而是】语言强制"自定义构造必须对全字段负责"。默认初始化机制没被关掉，是"选了自定义构造这条路，语言要求你负责到底"。
- ⚠ 构造函数 ≠ 默认值兜底（两轮追问掰开的核心）：
  字段变默认值(0/null) = 【默认初始化(内存层)】的功劳，class/struct 都一样，与构造函数无关。
  构造函数只负责"new 时你想额外做的初始化逻辑"。
  class 没写构造时编译器送一个【空的】public 无参构造(只为能 new，不负责清零)；
  一旦自己写了任意构造，编译器不再自动送无参构造(new Player() 会编译不过，除非自己补)。

### Unity

#### MonoBehaviour 生命周期 错点 / 缺口清单 √

**误区正误:**

**错:** FixedUpdate 排在 LateUpdate 之后(整条链最末尾)
**正:** FixedUpdate 在 Update 之前。完整时序:(每帧开头)FixedUpdate×N → Update → LateUpdate

**错:** GetKeyDown 放 FixedUpdate 顶多是"性能消耗/执行多次"
**正:** 放 FixedUpdate 会漏读(该帧 fix 跑0次→按下信号整个丢失)或重读(跑多次→一次按下触发多下)。GetKeyDown 只能放 Update,因为"按下"信号按渲染帧发放,只有 Update 同频

**错:** 两个对象跨脚本时,感觉 Awake 读别人和 Start 读别人"都行"
**正:** 跨对象的 Awake 之间无顺序保证。"依赖别的对象已初始化好"的操作必须放 Start,靠"全场 Awake 先于全场 Start"兜底

**机制补录(非错点,是本轮新钉准/易记错的边界):**

**补:** FixedUpdate 一个渲染帧里执行 0~N 次(不是固定1次)。机制=时间累加器:每帧把 deltaTime 加进累加器,攒够0.02就跑一次fix并减0.02,不够就0次。高帧率下不是"永不执行",是"每攒够0.02执行一次",平均每秒恒定50次

**补:** "全场 Awake 先于全场 Start"只对"同一批一起进场景的对象"成立。运行中途单独 Instantiate 的对象,只保证自己内部 Awake→Start 顺序,不保证与场景中其他对象的相对时序(别的对象可能早已跑完Start)

**补:** Awake vs Start 触发条件差异——Awake 对象创建时就调(哪怕脚本disabled);Start 在第一次Update前调、且要求脚本enabled

**补:** OnDisable/OnDestroy 与 OnEnable 对称,是 -= 取消订阅、释放资源处(呼应 OnEnable+=/OnDisable-= 铁律)

#### Prefab 错点 / 缺口清单

**误区正误:**

**错:** runtime(游戏运行时)在代码里改 Prefab 资产,已 Instantiate 出去的实例会跟着更新
**正:** 不会。实例出生后即与图纸脱钩,是内存中独立对象,收不到图纸改动通知。运行时让已存在实例全体变化→拿到引用逐个操作实例,或用事件广播让它们自己响应。("编辑器期改Prefab所有实例跟着变"是编辑器同步便利,别当runtime也成立)

**错:** 给10个敌人加"受击闪红"这种操作,ScriptableObject 也能做
**正:** 做不了。SO=纯数据容器,不进场景、无Transform、不渲染、不跑Update,无法执行运行时行为。加特效/换组件/改行为→改Prefab;改数值/配置/一张表→用SO。两者常配合(Prefab挂脚本引用SO读数值),非互相替代

**机制补录(非错点,是本轮新钉准/易记错的边界):**

**补:** Prefab 实例属性覆写(override)——改图纸后个别实例不跟着变,是因为该属性在这个实例上被单独override过(Inspector里蓝色竖线+加粗),已与图纸脱钩。想恢复跟随→对该属性Revert还原

**补:** 两种override同一内核——Variant的override=子图纸盖父图纸;实例的override=成品盖图纸。都是"覆写的归自己、没覆写的跟随上游",同C#继承override心智模型

**补:** Prefab=图纸(硬盘上.prefab资源,不在场景不运行);实例=照图纸造的GameObject(在场景、渲染、跑逻辑)。Instantiate=new一个实例。菜单3D Object拖出的Cube不是Prefab(是内置一次性组装,无.prefab文件),除非自己拖进Project存成Prefab

#### 坐标系与坐标转换 错点 / 缺口清单

**误区正误:**

**错:** 让UI血条跟随3D玩家 → 世界坐标转视口坐标
**正:** 世界坐标转屏幕坐标(WorldToScreenPoint)。视口是0~1比例、非像素,拿去摆UI还差一步;UI最终按屏幕像素摆位,所以要屏幕坐标。血条/伤害数字/头顶名字全靠这个

**错:** 鼠标点击选中3D物体 → 屏幕坐标转"本地坐标"
**正:** 屏幕坐标转"世界空间射线"。本地坐标(localPosition)是子物体相对父物体的概念,与"从屏幕射进3D世界"无关,别混。正确链条:鼠标屏幕坐标 → ScreenPointToRay生成世界空间射线 → Physics.Raycast检测世界碰撞体 → 命中物体

**机制补录(非错点,是本轮新钉准/易记错的边界):**

**补:** 本地坐标(localPosition)= 相对父对象坐标系(父的Transform:位置+旋转+缩放)的偏移,不只是"相对父中心点"。父无旋转无缩放时说"父中心点"不出错;父一旦旋转/缩放,子的世界位置要跟着父一起转、一起缩放

**补:** 视口坐标(Viewport)——左下(0,0)、右上(1,1),0~1归一化比例,屏幕正中(0.5,0.5)。好处=不依赖分辨率("永远贴右上角"用视口(1,1)一劳永逸)。屏幕坐标则是像素、右上(Screen.width, Screen.height)

视口坐标最正统的家在**摄像机的 Viewport Rect**(分屏、小地图);其次是**判断物体在不在屏幕内**(WorldToViewportPoint 看落没落在 0~1)。特征永远是那句——**要相对比例、不要管分辨率,就用它。**

**补:** 屏幕坐标原点左下(0,0)、右上(Screen.width,Screen.height)、单位像素。("左下原点"要记牢,后面撞UI锚点/RectTransform时注意与其他坐标系原点位置的差异)

### 分解能力(decomposition)

**那个"脑子里自动出现步骤流"的能力,真名叫什么:**

它不是记忆,是**分解能力(decomposition)**——拿到一个大需求,能把它拆成"要素 → 子步骤 → 顺序"的能力。这个能力**不是背出来的,是练出来的**,而且有具体练法。我今天推你走的那些问题(先做什么、这一步依赖什么、这个之前必须有什么),其实就是**分解的思考动作**。你要学的不是那些步骤的答案,是**那些提问本身**——把我问你的问题,变成你问自己的问题。

### 内存泄漏(memory leak)

术语:**内存泄漏(memory leak)**。这个具体形式叫**事件导致的内存泄漏**,或者更细的名字——**失效监听器 / lapsed listener**(订阅者已经"失效"了,但监听关系还赖着不走)。你说"可能没见过",正常,这是个偏工程经验的词,不是语法点,查一次记住就行,不算缺口。

补一个 Unity 语境下的重点,因为这直接关系你以后写代码会不会踩:

MonoBehaviour(比如 A 是个挂在 GameObject 上的脚本)的情况更阴。你 `Destroy` 了那个 GameObject,Unity 层面它"没了"——但如果某个长命的事件(挂在全局管理器、单例上)还订阅着 A 的方法,**C# 这边的托管对象 A 根本没被回收**,它被订阅列表引用着。结果是:一个你以为已经销毁的对象,事件一触发,它的方法照样被调用,而它内部访问的东西可能已经是残废状态 → 抛异常,或者更糟,悄悄执行了不该执行的逻辑。这就是为什么 Unity 里 `OnEnable` 里 `+=`、`OnDisable`/`OnDestroy` 里 `-=` 是条铁律——成对出现,谁订阅谁负责退订。

你之前学的事件中心 / 消息系统,如果临摹过,里面八成有一套"移除监听"的接口,原因就是这个。

---

顺带点一个 Unity 里的现实后果,不用深挖,先埋个印象:正因为堆对象靠 GC 回收、而 GC 触发时会有开销(可能造成帧率卡顿,俗称"GC 尖峰"),所以 Unity 性能优化里有一大块就是"**减少堆分配、别频繁 new**"——比如别在 Update 里每帧 new 对象。这直接连回你刚问的:每 new 一次堆上开一块,new 得太勤 → 垃圾产生快 → GC 来得勤 → 卡顿。现在只要记住"堆分配有代价、GC 有开销"就够,以后讲优化会回来。
