##### 0. 一句话速记

用代码建 mesh = 往 Mesh 填三组数据：**vertices**（`Vector3[]`，本地坐标）、**triangles**（`int[]`，存顶点索引，每 3 个索引 = 1 个三角形面）、**uv**（可选，贴图映射）。 圆柱隧道 = **一圈一圈**顶点沿 z 轴排开（sin/cos 摆圆 + z 递增），再把**相邻两圈**的顶点用索引连成三角形面。

---

##### 1. 核心表

**三组数据**

|数据|类型|存什么|关键点|
|---|---|---|---|
|vertices|`Vector3[]`|每个顶点的**本地坐标**|不是世界坐标；Transform 管变换|
|triangles|`int[]`|顶点在 vertices 里的**索引**|每 3 个 = 1 三角形；长度 = 三角形数 × 3；索引可重复（共用边）|
|uv|`Vector2[]`|顶点在贴图上的位置（0~1）|与 vertices 一一对应；不贴图可略|

**圆柱 mesh 关键量**（countX = 圆周段数，countZ = 沿轴段数）

|量|表达式|含义|
|---|---|---|
|每圈点数|`countX + 1`|圆周 countX 段 → countX+1 个点|
|总圈数|`countZ + 1`|z 方向 countZ 段 → countZ+1 圈|
|顶点总数|`(countX+1) × (countZ+1)`|数组开这么大|
|格子数|`countX × countZ`|n 桩夹 n-1 段|
|triangles 数组长度|`countX × countZ × 6`|每格 2 三角形 × 3 索引|
|单份角度|`2π / countX`|相邻两点圆心夹角（**弧度**）|

---

##### 2. 原理 / 几何意义

**① 顶点存本地坐标（可推导）** 反证：若存世界坐标，把物体拖走 / 旋转时，顶点数组该整个变；但实际一个数都不变——所以存的是**本地坐标**，由 Transform（位/旋/缩）变换到世界。这正是网格能复用、能摆到任意位置的原因。

**② triangles 存索引（可推导）** triangles 是 `int[]`，一个 `int` 装不下 `Vector3`（3 个 float）→ 只能存**下标**，靠下标去 vertices 里取真正的坐标。间接引用。

**③ 一圈顶点坐标（sin/cos）**

- 相邻两顶点圆心夹角 = `2π / n`（整圈均分给 n 个）。
- 第 i 个顶点转过总角度 `θ = i × (2π/n)`。
- 直角三角形推坐标：`x = sinθ · r`（对边）、`y = cosθ · r`（邻边）。
- z（沿隧道延伸）：`z = 圈号 × 间隔`。

**④ 绕序 → 朝向** 三个顶点的**顺序**决定这个三角形的法线朝向 / 哪一面被渲染。“顺 / 逆时针对应正面”是**依赖视角的滑标签**，不背——**看穿了就把绕序反过来试**（见 §5）。

**⑤ triangles 构建：四角偏移（本知识点最难，重点记）** 顶点**按圈连续存**（第 0 圈：索引 0~countX；第 1 圈：countX+1 起……）。所以：

- **同圈右邻** = `+1`
- **前一圈同角度** = `+ (countX+1)`（每圈点数）

一个格子四个角（current = 左下角索引）：

```
        左上                 右上
   current+(countX+1)  current+(countX+1)+1
        |                     |
       左下 ───────────────── 右下
     current              current+1
```

- 一个格子拆成 **2 个三角形**，二者**共用同一条对角线、各占一半**（不重不漏）。
- `current = (countX+1) × z + x`（第 z 圈第 x 个点的索引，与顶点循环 index 排布一致）。

---

##### 3. 精髓 / 边界

**数据的存储顺序，要服务于将来在它上面跑的算法。** 按圈存（外层 z、内层 x）：相邻圈对应点索引差 = 每圈点数（`current + 6`），规律整齐，triangles 好写。 按纵线存（外层 x、内层 z）：同一圈的点在数组里隔一整条纵线、零散，triangles 索引要跳着算、极易错。 → 两种都能存下全部顶点，按圈存**不是唯一正确，是更省事，优先选**。“能做但选更省事的”本身就是工程判断。

---

##### 4. 选型映射

**`mesh` vs `sharedMesh`**

|特征 →|用哪个|
|---|---|
|要**单独改**某个物体的网格|`mesh`（拿专属拷贝，不连累其他共用者）|
|只读 / 想让所有共用者**一起变** / 编辑器里操作资源|`sharedMesh`（碰共享原件）|

**对角线选哪条**：`6—1` 或 `0—7` 都行，只要两个三角形共用它、各占一半。

##### 5. 关键细节 / 陷阱

- **背面剔除**：绕反了**不是变黑**，是那一面根本不渲染 → **看穿**到背后。看不见先反绕序试。
- **`mesh` vs `sharedMesh` 的坑**：读 `filter.mesh` 每次给你一份**拷贝**（循环里反复读 → 内存堆一堆拷贝 → 泄漏）；改 `sharedMesh` 会改到**所有共用者 + 磁盘上的 Prefab 资源**（编辑器里尤其危险）。属“拷贝 vs 原件”思维类型，同 `DontDestroyOnLoad` 状态残留。
- **弧度制**：`Mathf.Sin/Cos` 吃**弧度**不是角度；`Mathf.Sin(90)` 会当 **90 弧度**算。手里是角度先 `× Mathf.Deg2Rad`。**更根本**：直接用弧度建模（2π 整圈 / π 半圈 / π/2 直角 / 2π/n 均分），根本没有“转换”这步。（⚠ 弧度未成直觉是**待专项重建**的缺口，不是查一下就好）
- **fencepost（今日踩 3 次）**：**顶点**方向 +1（countX+1 点 / countZ+1 圈）；**格子**方向不 +1（countX / countZ）。循环用 `< countX` / `< countZ`。
- **四角偏移易混**：`+1` = 同圈右邻（下排）；`+(countX+1)` = 跨圈（上排 / 前一圈）。**错在“哪一圈”，与顺/逆时针无关**——顺逆只影响“左/右”，不影响“上/下（哪一圈）”，z 坐标是铁证。
- **两三角形共用对角线**、各占一半（描一遍验不重不漏，别凭感觉）。
- **两三角形绕序要一致**（都朝里 / 都朝外）；不一致 → 每格只显示一半，呈**规则镂空**（整齐镂空 = 索引对、只是绕序没统一）。
- **`countX` / `countZ` 命名太像 → 高频手误**（今日 X/Z 混淆 3+ 次）。写完扫一遍“每个 count 是不是该有的那个”，或起更区分的名。
- **for 三段**（初始 / 判断 / 自增）必须**同一变量**（曾把内层 `x` 的自增写成 `z++` → 死循环 + 越界）。
- **`++i` vs `i++`**：嵌在表达式里（`arr[i++]` 当下标）**有区别**——后增先用当前值、前增会先加导致跳位 / 越界；单独成句（`i++;`）**无区别**。“++i 性能更好”对 **C# int 不成立**（那是 C++ 重迭代器的事，int 上等价）。选择依据是“有没有嵌在表达式里”，嵌下标必用 `i++`。

##### 6. 应用速查

**从零生成圆柱 mesh 的步骤**

|步|做什么|关键|
|---|---|---|
|1|`GetComponent<MeshFilter>()` + `new Mesh()` 挂上|Mesh 槽**代码填**，不在 Inspector 拖|
|2|给 MeshRenderer 材质|没材质 = **紫色**占位|
|3|双层循环生成顶点|外层 z（圈）、内层 x（点）；`x/y = sin/cos·r`，`z = 圈号·间隔`|
|4|`mesh.vertices = 数组`|局部数组**必须赋给 mesh**，否则白算|
|5|双层循环建 triangles|`current` + 四角偏移，每格塞 6 索引；**独立写入指针**（别拿 current 当写入位置）|
|6|`mesh.triangles = 数组`|看不见就**反绕序**|
|7|（可选）`RecalculateNormals()` / uv|光照正确 / 贴图对齐|

##### 7. 踩过的错（错 → 正）

- 顶点坐标：**世界** → **本地**（Transform 管变换）
- triangles：**存坐标** → **存索引**（int 下标）
- 绕反现象：**变黑** → **背面剔除、看穿**
- sharedMesh：**着色** → **共享原件**
- 一圈坐标：**弧长算 xy** → **夹角 + sin/cos**
- Sin/Cos 单位：**角度** → **弧度**（`× Deg2Rad`）
- 四角偏移：**右下 = +每圈点数 / 左上 = +1** → **右下 = +1 / 左上 = +每圈点数**（错在哪一圈，与顺逆无关）
- 格子 fencepost：**格子数 = 顶点数** → **格子 = countX × countZ**（n 桩夹 n-1 段）
- `++i` / `i++`：**以为 ++i 更快** → **int 上等价，按语义选**（嵌下标必 `i++`）
- （手误类，非概念错）`countX` / `countZ` 写混；for 自增写成另一变量

**① 误区 / 纠正**

- **新块首圈 z（本轮最顽固，摔三次）**：反复答“= 旧块末圈 z（相等）” → 纠：**= 旧块末圈 z + 一个圈间隔**。过程：“就是旧块 z 值” → 纠 → “等于末圈 z” → 借“首末都有顶点”翻案 → 最终锁定“末圈 + 一个间隔”。相等 → 两圈落同一 z、**重叠**。（§2 / §5）
- **A/B 概念串了**：画图时冒出“新块 z = 末圈 z + **隧道长度一半**” → 纠：那是把“**每圈各自的 z**”（本项目用法）和“**整块的位置**”两个概念串了。本项目 z 是**每个顶点各自的坐标**，不存在“整块中心”，故是“末圈 + 一个间隔”，不是“半块长”。（§2 / §5）
- **countZ 语义**：初认“countZ = **圈数**” → 纠：**countZ = 间隔数，实际圈数 = countZ + 1**，末圈 z = countZ × 间隔。（fencepost，§5）

**② 遗漏 / 初次接触（讲解后才补上因果）**

- **新块 xyz 混合取法的 why**：初次闭卷调不出（明确“不知道”），经引导推出——**xy 取旧块末尾圈**（对齐柏林凹凸）、**z 接末尾 + 间隔**（防重叠续延伸）。（§2）

##### 0. 一句话速记

无限 = 用**两块**地形循环复用伪造。**地动车不动**（地形往后位移）。车走到后一块偏前 → **移除旧块 + 在最前端接新块**。新块起点：**xy 取旧块末尾圈**（接缝对齐防断层）、**z = 旧块末圈 z + 一个间隔**（防重叠续延伸），接缝后几圈 **Lerp** 平滑过渡。

##### 1. 核心表

**新块起点各分量取值来源（本知识点的心脏）**

|分量|取自|为什么|
|---|---|---|
|x, y|旧块**末尾那圈**的对应值|对齐柏林噪声凹凸，接缝**横向 / 高度对齐**、防断层|
|z|旧块末圈 z **+ 一个圈间隔**|防两块**重叠** + 继续往前**延伸**|
|（接缝后若干圈）|Lerp：旧块末尾高度 → 新块本高度|硬接有急转，**平滑过渡**|

**一句话记**：z 管“接着往前不重叠”，xy 管“接缝对齐不断层”，Lerp 管“接缝后平滑过渡”。三方向各司其职 → 所以是**混合取法**，不是三个都取同一点。

**双缓冲关键量**

|量|值|说明|
|---|---|---|
|同时存在的块|最多 2 块（0 / 1 循环）|双缓冲|
|谁在动|地形往后位移，车原地|地动非车动|
|触发替换|车到后一块“起点偏前”|空对象标记该点、作块的子物体|
|移除时机约束|视野内不穿帮|移早了摄像机拍到隧道外|

---

##### 2. 原理 / 几何意义

**① 双缓冲 + 地动** 不可能真生成无限长网格 → 只保留两块、循环复用。小车前进的错觉靠**地形整体往后位移**（车原地），不是车往前移。这是这类无限地形的核心诡计。

**② 触发替换** 车（相对地形）走到后一块的“起点偏前”位置 → 移除旧块 + 在最前端接新块。用一个**空对象标记这个触发点**、作为地图块的**子物体**（跟着块走，位置自动相对，不用手算世界坐标）。

**③ 新块起点 xyz —— 为什么是混合取法** 一块 = 很多圈顶点沿 z 铺开。“接得上”这件事，三个方向要求不同：

- **z（延伸方向）**：旧块铺到某 z 结束，新块必须从**旧块末圈 z 接着往下铺**（末圈 + 一个间隔）。若从自己内部圈号（0,1,2…）重算 → 铺回原点附近、和旧块**在 z 上重叠**。
- **y（高度，被柏林噪声顶得凹凸）**：新块第一圈若**独立算自己高度**，值和旧块末圈**大概率不同** → 接缝**断层 / 台阶**。故第一圈高度必须**接过旧块末圈高度**，接缝处**相等**、平滑。x（横向偏移）同理。
- **Lerp**：只让接缝**一圈**对齐还不够——第二圈若立刻跳回新块自己的噪声高度会有**突兀急转**。故接缝后**若干圈用 Lerp**，从“旧块末尾高度”逐渐渐变到“新块本该有的高度”。

**④ 为什么 z 是“+一个间隔”不是“相等”** 块内圈与圈之间隔“一个间隔”排开（第 0、1 圈差一个间隔…）。新块首圈是“接着旧块末圈的**下一圈**”，和末圈之间也得是**一个间隔**——跟块内圈距一致才严丝合缝、均匀。差 0（相等）→ 重叠；差一个间隔 → 接上。

---

##### 3. 精髓 / 边界

**接续 ≠ 相等，差一个步长。** 这是本知识点最顽固的坑（摔三次）。“新块接旧块”“下一圈接当前圈”这类**接续**关系，永远是“末尾 + 一个步长”，不是“等于末尾”。相等 = 重叠。凡遇到“接上 / 续延”的坐标，先反问：是不是漏了那**一个间隔**？

##### 5. 关键细节 / 陷阱

- **z “相等 vs +间隔”（顽固，摔三次）**：新块首圈 z = 旧块末圈 z **+ 一个间隔**，不是相等。相等 → 两圈落同一 z、重叠。记死“接续差一个步长”。
- **A / B 概念别串**：本项目 z 是**每个顶点各自的坐标**（每圈递增），**不是整块的位置**。所以是“末圈 + 一个间隔”，不存在“整块中心 / 半块长”那套（那是“整块当一个物体摆位置”的另一种建模）。混了就会算出“加隧道长度一半”这种错。
- **countZ = 间隔数（fencepost）**：countZ 是**间隔数**，圈数 = **countZ + 1**，末圈 z = countZ × 间隔（不是 (countZ−1) × 间隔）。
    - ⚠ **与《程序化网格生成》笔记里那条 fencepost 区分**：那条是“格子数 = countX × countZ”（顶点 vs 格子）；**这条**是“圈数 = countZ + 1”（间隔 vs 圈），用来定**末圈 z**。同是“桩 vs 段”关系，但用在不同处——别因为那边已有 fencepost 就漏了这条。
- **移除时机**：移早了 → 摄像机拍到隧道外**穿帮**。用空对象标记触发点约束“什么时候移”。
- **单圈对齐 ≠ 平滑**：xy 取末尾让接缝“横向 + 高度”对上；但单圈对齐后仍需 **Lerp 过渡后续几圈**，否则第二圈就跳回自身噪声高度、出现急转。

##### 0. 一句话速记

- **委托 = 存“方法”的类型**（像变量，但装的是方法），可 `d()` 或 `d?.Invoke()` 调用。
- **事件 = 加了 `event` 修饰符的委托**，多一层保护：**外部只能 `+=`/`-=`，不能 `=`、不能触发**；只有声明它的类内部能触发。
- 核心价值：**解耦**——触发方不需要知道谁在监听。

##### 1. 核心表

|委托 delegate|事件 event|
|---|---|---|
|本质|存方法的类型|加 `event` 的委托|
|外部能否 `=` 覆盖|能（危险，会清空别人订阅）|**不能**|
|外部能否触发 Invoke|能|**不能**（只有声明类内部能触发）|
|外部能否 `+=`/`-=`|能|能（外部唯一能做的）|
|用途|通用“方法容器”|对外暴露的、受保护的通知点|

**Action / Func 分轴（易混，钉死）**：

|有无返回值|例|泛型上限|
|---|---|---|---|
|`Action`|**无返回值**(void)|`Action`、`Action<T>`、`Action<T1,T2>`|16 个入参|
|`Func`|**有返回值**|`Func<TResult>`、`Func<T,TResult>`（最后一个泛型是返回类型）|16 个入参 + 1 返回|
|`Predicate<T>`|返回 bool|判断用|—|

> 分轴是**返回值**，不是“有没有参数”——两者都能带参。

##### 2. 原理 / 机制

- **委托为什么能“存方法”**：委托类型的实例内部持有一个（或一串）方法引用。`d += A.Foo` 就是把 `A.Foo` 加进这条调用列表；`d()` 触发时，列表里的方法被依次调用。
- **事件为什么“更安全”**——从“如果直接暴露裸委托会怎样”推：
    - 裸委托暴露给外部 → 外部能 `field = null` 一把清空所有人的订阅、能随意 `field.Invoke()` 冒充触发。
    - 加 `event` 后，编译器只对外开放 `+=`/`-=`，堵住 `=` 和触发。→ **所以 event 的“安全”不是背的，是“把危险操作关掉”的结果。**
- **内存泄漏机制（从例子推，不背）**：
    - 事件的订阅列表里，每个订阅项 = “某对象 + 它的某方法”，即**持有一个指向订阅者对象的引用**。
    - GC 回收一个堆对象的判据 = “还有没有人引用它”。
    - 若订阅者用完（甚至已 `Destroy`）却没 `-=`，而事件活得久（挂在全局/单例）→ 订阅列表**一直攥着这个引用** → 对象回收不掉 → 泄漏。

##### 5. 关键细节 / 陷阱

- **`= vs +=`**：
    - 外部类对事件用 `=` → 编译错误（CS0070）。外部只能 `+=`/`-=`。
    - 声明类**内部**，字段式事件（`public event UnityAction e;` 这种直接一行、没写 add/remove 的）中 `e` 就是编译器生成的那个私有委托字段，内部 `=`/触发都合法。
- **裸调 null 委托会 NRE**：没有任何订阅者时 `e()` 抛异常 → 用 `e?.Invoke()` 空安全触发。
- **内存泄漏 ≠ 崩溃**（本轮专门对齐的点）：
    - 泄漏 = 该回收的内存没回收、持续占用（一种**状态**）。
    - 崩溃(OOM) 只是泄漏累积到耗尽内存时的**可能**后果，非必然、非最常见。典型表现更多是内存走高、越用越卡、掉帧、系统杀后台（尤其移动端）。
- **事件泄漏危害有两条腿**（别只记内存）：
    - ① 占内存（可能累积到崩）。
    - ② **僵尸对象被继续调用**：对象没被回收，事件一触发照样调它的方法 → 访问已残废状态 → 逻辑 bug。这条与内存涨不涨无关，独立发生。
- **术语**：事件导致的内存泄漏 / **lapsed listener（失效监听器）**。查一次即可，非缺口。
- **Unity 关联（另见 Unity 复习）**：MonoBehaviour 被 Destroy 但长命事件仍订阅 → 托管对象不回收 + 触发时访问残废状态。铁律：`OnEnable` 里 `+=` / `OnDisable`(或 `OnDestroy`) 里 `-=`，**成对**，谁订阅谁退订。

##### 7. 踩过的错（错 → 正）

- 错：Action/Func 按“有参无参”分 → 正：按**有无返回值**分（Action 无返回值、Func 有）。
- 错：事件泄漏只想到“多执行一次方法” → 正：根子是**订阅列表持有引用致对象回收不掉**（泄漏）+ **僵尸对象被调用**（逻辑 bug），两条腿。

##### 0. 一句话速记

- 协程 = **协同程序**，在**主线程上**分步执行的“伪并发”，**不开新线程**。
- 关键：**主线程从不停**。协程执行到 `yield return` → **协程把自己挂起、让出** → 主线程继续跑别的 → 条件达成后主线程回来，从上次挂起处接着跑。
- 与多线程的根本区别：多线程真并行（另开线程）；协程只是**分帧**，活还在主线程上。

##### 1. 核心参考

|协程|多线程|
|---|---|---|
|是否开新线程|否，在主线程|是|
|并发性质|伪并发（分步/分帧）|真并行|
|能否做重计算不卡|**不能**（重活占死那一帧）|能（活在别的线程）|
|典型用途|分帧加载、延时、按帧推进的流程|CPU 密集计算|

##### 2. 原理 / 机制

- **执行流程（从一段最小协程推）**：
    
    ```
    print(i); i+=10;      // 进入协程先跑到这yield return null;    // 协程在此挂起、让出；主线程继续跑它自己的print(i);             // 下一帧（或条件达成）主线程回来，从这继续
    ```
    
    没有更多 `yield` → 协程执行完毕。**若 `yield` 在死循环里 → 协程永不结束。**
- **谁挂起谁（钉死）**：挂起的是**协程**，让出的是**协程**，主线程**没停**。协程是“主动让出、时机到再被接回”，不是“占用主线程去跑自己”。
- **`yield return` 后面值 → 按【类型】决定等待策略**（忘过，补）：
    - `YieldInstruction` 子类（`WaitForSeconds` / `WaitForFixedUpdate` / `WaitForEndOfFrame`）→ 按各自规则等。
    - 另一个 `IEnumerator`（嵌套协程）→ 等那个子协程跑完。
    - `null` → 等下一帧。
    - **其他任意类型（如 `int 0`）→ Unity 不识别，降级当 `null` 处理 → 也等一帧。**

##### 5. 关键细节 / 陷阱

- **`yield return 0` 与 `yield return null` 表现相同**（0 被当 null）——但**语义**上应写 `null`；写 `0` 会误导读者以为“等 0 秒”。行为无差、可读性有差。
- **协程不能做重计算**：它在主线程，某一步里跑 500ms 的循环 → 那一帧被占死、照样卡。协程只能“**分帧**”不能“**分线程**”。真要压榨 CPU 的重活 → 真多线程 / Job System。
- **内存泄漏方向（与事件相反，勿混）**：协程被 Unity 自己调度管理，宿主对象销毁时一并清理，不存在“外部长命列表攥引用”的泄漏结构。协程的坑是**没料到就停**（见 Unity 篇），不是泄漏。
- **Unity 相关（另见 Unity 复习）**：谁驱动（Unity 每帧 MoveNext）、生命周期绑定（GameObject Destroy / 组件 SetActive(false) → 协程静默停止）、`StopCoroutine` 与 `StartCoroutine` 的配对坑。

##### 7. 踩过的错（错 → 正）

- 错：`yield return` 是“挂起主线程去跑协程” → 正：挂起的是**协程自己**、主线程没停，协程**让出**、时机到再被接回。
- 错：协程会像事件那样内存泄漏 → 正：**方向相反**，协程的坑是**静默停止**，不是赖着泄漏。

##### ★ 本轮摸底实录（误区/纠正 + 遗漏）

**① 误区 / 纠正**

- **“值类型 = 栈”不准确**：初答把“值类型”这个类型属性和“存栈”这个位置绑死。→ 纠正：**存储位置由“变量寄居在哪个上下文”决定**——局部变量在栈；对象的字段 / 数组元素跟着对象在**堆**（值类型字段也在堆）。（详见 2. ）

##### 0. 一句话速记

- **值类型**：变量格子里装**数据本身**。赋值/传参 = **拷贝一整份数据**，两份独立。（int/float/bool/struct、枚举…）
- **引用类型**：变量格子里装**地址**，地址指向堆上的对象。赋值/传参 = **拷贝地址**，多个格子指向同一个对象。（class、数组、string、委托…）
- 一句判据：**“值 vs 引用”决定的是“拷贝数据还是拷贝地址”（语义），不直接决定“存栈还是堆”（位置）。**

##### 1. 核心表

|值类型|引用类型|
|---|---|---|
|格子里装什么|数据本身|地址（指向堆上对象）|
|赋值 `b = a`|拷贝数据，两份独立|拷贝地址，指同一对象|
|改一个影响另一个吗|不影响|影响（同一对象）|
|能否为 null|不能（它就是数据）|能（可空着不指向）|
|典型|int/float/bool/struct/枚举|class/数组/string/委托|

##### 2. 原理 / 机制（核心图，钉死）

**变量/格子（栈） vs 对象（堆）**——用“手 / 房子”想：

```
        栈(Stack)                  堆(Heap)
   ┌──────────────┐         ┌────────────────────┐
   │ e = 0x1000   │───────▶ │ 0x1000: Enemy 对象  │
   │ (存的是地址)  │         │        level = 0    │
   └──────────────┘         └────────────────────┘
```

- **变量 `e`** = 栈上的格子，装着一个**地址**（“拿着地址的手”）。
- **`new Enemy()`** = 堆上真实对象（“手指向的房子”），里面含它的字段。
- **铁律**：只有 `new` 在堆上造对象；赋值(`=`)**从不造对象**，只抄格子内容（值→抄数据，引用→抄地址）。数“堆上有几个对象”= 数执行了几次 `new`。

**存储位置由“寄居上下文”决定，不由“是不是值类型”决定**：

- 局部变量 → 栈；
- 对象的字段 / 数组元素 → 跟着对象在**堆**（哪怕字段是 int 这种值类型）；
- 引用类型的“对象本体”在堆，指向它的“引用变量”若是局部变量则在栈（栈放地址、地址指堆）。

> 打开这扇门（值类型也可能在堆）后，**装箱**才讲得通——int 装箱后作为堆对象存在。

##### 5. 关键细节 / 陷阱

**赋值行为**（`Enemy a = new(); Enemy b = a;`）：一栋对象、两个格子(a/b)存同一地址；改 `b.level` 则 `a.level` 变（动的是同一对象）。

**传参（默认都是“值传递” = 传格子内容的拷贝）**——最反直觉、必记：

- `Change(a)` 传的是 **a 格子内容的拷贝**到新格子 `x`；`x ≠ a`，是两个格子。值类型拷贝数据、引用类型拷贝地址（两格子指同一对象）。
- **情况一** `x.level = 99;`（顺着地址改对象）→ 外面**看得到**（同一个对象）。
- **情况二** `x = new Enemy();`（让 x 改指新对象）→ 只动了 x 这个副本格子，**没动 a** → 外面**看不到**，a 仍指原对象。
- 一句话：**顺地址改对象 = 外部可见；改副本格子自己的指向 = 外部不可见。**

**生命周期 / 释放**（栈 vs 堆最本质区别）：

- **栈**：出作用域**立即、自动、零成本**释放（栈帧弹出），不需要 GC。局部值类型变量、引用变量本身都在此列。
- **堆**：对象在“**无任何引用指向它**”后成为垃圾，等 GC 在**不确定时机**回收。非确定性。
- 后果（埋点，接性能优化）：`new` 得勤 → 垃圾多 → GC 勤 → 卡顿（GC 尖峰）。优化方向：减少堆分配、别在 Update 里频繁 new。

##### 7. 踩过的错（错 → 正）

- 错：“值类型 = 存栈” → 正：**位置由寄居上下文定**；对象字段/数组元素（含值类型字段）在堆。
- 错：`Change(a)` 传的是 a 格子本身 → 正：传 **a 格子内容的拷贝**（x 是副本，`x = new()` 不影响 a）。

#### 装箱与拆箱 复习笔记（完整版）

##### ★ 本轮摸底实录（误区/纠正 + 遗漏）

> **分工声明**：本区块 = 本轮当场卡点/错点/遗漏（时间轴锚点）；下面正文 = 知识该长的样子（长期复习）。不合并、不互替。

**② 遗漏 / 初次接触 / 补正**

- **“拷贝、两份独立”这层**：初答只说“堆开格子存值”，没点出装箱是**把值拷贝进堆、栈堆两份独立**。补上（实测题确认：`object o=i; i=20;` 后 o 仍是原值）。→ 见 §2

##### 0. 一句话速记

- **装箱 boxing**：值类型 → `object`（或接口）。在**堆**上新开空间、把值**拷贝**进去，引用存该堆对象地址。
- **拆箱 unboxing**：`object` → 值类型，把堆里的值**拷贝**回栈上值类型变量，**必须显式强转**。
- 两次都是**拷贝**；箱子里的类型**焊死**，拆箱必须按装入时的确切类型。

##### 2 原理 / 机制（从例子推，不背）

```csharp
int i = 10;
object o = i;   // 装箱：堆上开空间，把 10 拷贝进去，o 存该对象地址
int j = (int)o; // 拆箱：把堆里那份 10 拷回栈上，必须显式 (int)
```

- **装箱 = 拷贝、两份独立**（关键，初答漏的）：
    
    ```csharp
    int i = 10;object o = i;   // 把 10 拷进堆i = 20;         // 改栈上的 i// o 里仍是 10 —— 因为 o 指向堆里那份独立拷贝，与栈上的 i 无关
    ```
    
    装箱不是“把 i 移进堆”，也不是“堆引用了栈上的 i”——值类型没有“被别处引用”这回事，只会被**拷贝**。
- **箱子类型焊死**：`object o = 10;` 里箱子永远是 `int`。写 `o = "10";` 不是“把箱子里的 int 改成 string”，而是 **o 改指向一个新的 string 对象**（原 int 箱子失去引用、等 GC）。能变的是“o 指向谁”，不能变的是“每个箱子装的类型”。

##### 5. 关键细节 / 陷阱

- **拆箱必须报对类型**：
    
    ```csharp
    object o = 10;int x = (int)o;      // ✅ 按装入的确切类型double d = (double)o; // ❌ 运行时崩 InvalidCastException
    ```
    
    箱子记得自己装的是什么，拆时“报对暗号”才行。
- **拆箱的 `(int)` ≠ 数值转换**：`(int)o`（拆箱）是“我知道箱里是 int，原样取回”，**不做数值转换**；`(int)10.5`（double→int）才是真数值转换。别混。
- **性能真相**：装箱开销 = **堆分配 + 拷贝 + 日后 GC 回收**，不是“转换动作”本身。装箱是**隐蔽的堆分配**（看不见的 `new`）——在循环/`Update` 里频繁装箱 → 大量小垃圾 → GC 频繁 → 卡顿。

##### 4. 选型映射 / 如何避免

- **触发装箱的典型场景**：值类型被塞进 `object` 或非泛型集合；早期 `ArrayList` 存值类型；某些不带泛型重载的 API。
- **避免**：用泛型（见下）；避免不必要的 `object` 兜底；结构体实现接口后以接口调用也可能装箱，留意。

##### 7. 踩过的错（错 → 正）

- 错：装箱性能开销主要来自“类型转换动作” → 正：来自**堆分配 + GC**（装箱=隐蔽堆分配）。
- 错：只知“堆开格子存值”，以为装箱后堆里那份和栈上的 i 联动 → 正：是**拷贝、两份独立**，改 i 不影响 o。

##### ★ 本轮摸底实录（误区/纠正 + 遗漏）

> **分工声明**：本区块 = 本轮当场卡点/错点/遗漏（时间轴锚点）；下面正文 = 知识该长的样子（长期复习）。不合并、不互替。

**① 误区 / 纠正**（本轮一处概念混淆，值得记）

- **把“按下标访问”与“按值查找”混为一谈**：初答以为 `list[5]` 是 O(n)、要遍历。→ 纠正：**按下标 `list[5]` 是 O(1)**（数组连续、算地址直达）；**按值查找 `Contains`/`IndexOf` 才是 O(n)**（遍历）。纠正后能自主复述正确成本地图。属标签混淆、一提即回。（详见 §5、§6）

**② 遗漏 / 初次接触 / 补正**

- 扩容真实动作：初答“翻倍”对，补上“**新开数组 + 全量拷贝 + 旧数组丢弃**”。→ 见 §2
- 选型补正：List 中间/开头增删 O(n)（非强项）；Dictionary 按 key 增删 O(1)。→ 见 §4

##### 0. 一句话速记

- **List\<T>** = 底层**数组**（连续内存）。强在“**按下标 O(1) 随机访问**”和“有顺序、可遍历”。
- **Dictionary<TKey,TValue>** = 底层**哈希表**。强在“**按 key O(1) 查找/增删**”，不关心顺序。
- 一句选型：**要“按下标取第 N 个 / 按顺序遍历” → List；要“拿 key 查 value” → Dictionary。**

##### 1. 核心表

| List\<T>     | Dictionary<TKey,TValue>       |                      |
| ------------ | ----------------------------- | -------------------- |
| 底层           | 数组（连续内存）                      | 哈希表                  |
| 按下标/按 key 访问 | `list[i]` **O(1)**            | `dict[key]` **O(1)** |
| 按值查找         | `Contains`/`IndexOf` **O(n)** | 天生按 key，不适用“按值”      |
| 末尾增删         | O(1)（不扩容时）                    | —                    |
| 中间/开头增删      | **O(n)**（要移动后续元素）             | 按 key 增删 **O(1)**    |
| 有无顺序         | 有（插入顺序）                       | 无（不保证顺序）             |

##### 2. 原理 / 机制

- **List 扩容（从“数组连续”推）**：数组在内存里**连续**，后面那块可能被占，无法原地续。所以满了扩容 = **新开一个更大数组（一般翻倍）→ 把旧元素逐个拷贝过去 → 旧数组丢弃（等 GC）**。
    - 推论：已知规模就 `new List<T>(容量)` 预设，避免反复扩容拷贝。
- **Dictionary 为什么 O(1)（哈希映射本质）**：把 key 丢进**哈希函数** → 算出哈希值 → **直接映射到内部数组的某个下标** → value 存那儿。查时同一个 key 算出**同一个**下标，**直接跳过去取**，**不遍历**。**用计算代替查找**。
    - 哈希冲突：不同 key 可能算到同一下标 → 内部有机制处理（如同位置挂一条链）。先记主干。

##### 4. 选型映射（必有）

|需求特征|用哪个|为什么|
|---|---|---|
|要“第 N 个 / 按下标取”|List|下标 O(1)|
|要“从头到尾遍历、有顺序”|List|连续内存、有序|
|主要在末尾增删|List|末尾 O(1)|
|用某个 key/标识查对应数据|Dictionary|按 key O(1)|
|频繁按 key 增删、不关心顺序|Dictionary|按 key 增删 O(1)|
|频繁在开头/中间增删|**都别用 List 硬扛**|List 中间/开头 O(n)；视情况换结构|

- ✗ **废弃旧粗结论**“增删用 List、查找用 Dictionary”——它把 List 的中间增删短板误当强项。增删要分位置：List 只有末尾快。

##### 5. 关键细节 / 陷阱

- **成本地图（易错核心）**：
    - 按下标 `list[i]`：**O(1)**，与 i 大小无关（`起始地址 + i×元素大小`，一步算出、直接取）。
    - 末尾 Add（不扩容）：O(1)，前面元素不动；触发扩容那一次 O(n)（新数组+拷贝），**平摊**仍近 O(1)。
    - 中间/开头 插入或删除：**O(n)**，插入点之后所有元素要整体挪位。
    - 按值查找 `Contains`/`IndexOf`：**O(n)**，遍历。
- **两种“慢”别混**：扩容的慢（新数组+全量拷贝，偶发，可预设容量避免） ≠ 前插/中插的慢（移动插入点后所有元素，只要不在末尾就发生，**与扩容无关**）。
- **易混点根源（本轮的混淆，记牢）**：**“下标访问”≠“按值查找”**。`list[5]` 是 O(1)（直达）；`Contains(x)` 才是 O(n)（遍历）。混了就会误以为 `list[5]` 要遍历、误以为 List 增删是强项。

##### 6. 应用速查

|任务|用|怎么想|
|---|---|---|
|敌人按生成顺序、每帧遍历更新|`List<Enemy>`|有序 + 遍历|
|背包格子按位置排列、按格号取|`List<Item>`|下标 O(1)|
|用玩家 ID 查玩家数据|`Dictionary<int,Player>`|按 key O(1)|
|用物品名查配置|`Dictionary<string,ItemConfig>`|按 key O(1)|
|判断某元素在不在（无 key）|List 里是 O(n)；量大改用 `HashSet`|按值查找慢|

##### 7. 踩过的错（错 → 正）

- 错：`list[5]` 是 O(n)、要遍历 → 正：**O(1)**（算地址直达）；`Contains`/`IndexOf` 才是 O(n)。
- 错：“List 增删是强项” → 正：**只有末尾**增删 O(1)；中间/开头 O(n)。

##### 0. 一句话速记

- **`is`**：判断“是不是某类型”，返回 **bool**。
- **`as`**：引用类型/可空类型转换，“当成目标类型试试”；**失败给 `null`，不抛异常**。
- **`(Type)` 强转**：确信能转才用；**失败抛 `InvalidCastException`（崩）**。
- 分水岭：**强转失败=崩；as 失败=null。** 要“安全转、别崩” → `as` + 判 null，或 `is Type 变量` 模式匹配。

##### 1. 核心表

|作用|返回/结果|失败时|典型场景|
|---|---|---|---|---|
|`is`|判类型|bool|返回 false|只想知道“是不是”|
|`as`|引用/可空转换|目标类型 或 null|**返回 null**|不确定、失败是正常、不想崩|
|`(Type)`|强制转换|目标类型|**抛 InvalidCastException**|确信能转，转不了=bug 该暴露|

> `(Type)` 强转两种用途：① 有继承关系的向下转型（父→子，如 `object`→`Player`）；② 值类型的数值转换（`(int)3.14`）。

##### 2. 原理 / 机制（失败行为是核心）

```csharp
object obj = "hello";        // 里面其实是 string
Player p = obj as Player;    // as：转不了 → 不崩，p == null
Player q = (Player)obj;      // 强转：转不了 → 抛 InvalidCastException（崩）
```

- **选哪个 = 你想要哪种失败行为**：
    - **确定**它就是目标类型、转不了说明有 bug → 用**强转**（让它崩、早发现）。
    - **不确定**、转失败是正常情况、不想崩 → 用 **`as` + 判 null**。
- **验证遗忘 vs 空缺**：`"hello" as Player` 结果是 `null`（不崩）。答得出 = 遗忘（学过）；若猜“崩” = 可能没建立。本轮答对 → 遗忘。

##### 5. 关键细节 / 陷阱

- `as` 只能用于**引用类型 / 可空类型**（不能 `int as ...` 这种非可空值类型）。
- 强转失败的 `InvalidCastException` 是**运行时**异常，不是编译错误——编译能过、跑起来才崩。
- 别把“拆箱的 `(int)`”（原样取回、不做数值转换）和“数值强转 `(int)3.14`”混（详见装箱笔记）。

##### 6. 选型映射 / 标准写法（必有）

**需求：有个 `object obj`，怀疑是 `Player`，想安全转、失败也别崩。**

- **写法 A（as + 判 null）**：
    
    ```csharp
    Player p = obj as Player;if (p != null) { /* 用 p */ }
    ```
    
- **写法 B（模式匹配，现代 C# 首选，最简）**：
    
    ```csharp
    if (obj is Player p) { /* 是 Player 就转好赋给 p，一步到位，只查一次类型 */ }
    ```
    
- **写法 C（先 is 再强转，能用但查两次）**：
    
    ```csharp
    if (obj is Player) { Player p = (Player)obj; /* 已确认，强转不崩 */ }
    ```
    
- **反例**：`if (obj is Player) obj as Player;`——转换结果没接住（丢了），且查了两次类型。

|你想要|用|
|---|---|
|只判类型、拿 bool|`is`|
|安全转、失败别崩|`as`+判 null 或 `is Type 变量`|
|确信能转、转不了愿意崩（暴露 bug）|`(Type)` 强转|

##### 7. 踩过的错（错 → 正）

- 错：安全转写成 `if(obj is Player) obj as Player;`（结果没接住、查两次） → 正：`if (obj is Player p) { 用 p }` 或 `as` + 判 null。
- 错（遗漏）：说不出失败行为 → 正：**as 失败给 null；强转失败抛 InvalidCastException**。

##### 8. 闭卷自测（隔 2–3 天回来做）

2. `as` 转换失败会怎样？`(Type)` 强转失败会怎样？——两者失败行为的差异是这组的核心，说清。
3. `object obj = "hello"; Player p = obj as Player;`——崩吗？`p` 是什么？如果换成 `(Player)obj` 呢？

##### 0. 一句话速记

- **属性 = 伪装成字段的方法**：`obj.Hp = 100` 外表像给字段赋值，实际调用 **set 方法**；读 `obj.Hp` 调 **get 方法**。外表像字段（直接读写），内里是方法（能塞逻辑）。
- 价值：因为 get/set 是方法、能插代码 → 能做**校验 / 只读控制 / 读写附带逻辑**，这些**光秃字段做不到**。

##### 2. 原理 / 机制（从“字段做不到什么”推）

- **本质**：属性背后是一对方法（get/set）。所以任何“读写时想插一脚”的需求，属性能满足、字段不能。
- **三类字段做不到的事**：
    1. **校验**（set 里拦非法值）：
        
        ```csharp
        private int hp;public int Hp { get => hp; set { if (value < 0) value = 0; hp = value; } }
        ```
        
        `value` 是 set 里的**关键字**，代表“外面赋进来的那个值”。
    2. **只读 / 受控写**：
        
        ```csharp
        public int Hp { get; private set; } // 外部只能读，只有类内部能改
        ```
        
    3. **读写附带逻辑**：改血量时顺便刷血条 UI / 触发死亡判定，set 里可写任意代码。
- **自动属性 `{ get; set; }`**：当**不需要**任何额外逻辑时的偷懒写法，编译器**自动生成隐藏字段 + 标准 get/set**。
    - ⚠ 一旦 set 需要逻辑（校验/钳制/附带动作）→ **不能用自动属性**，必须展开成带字段的完整属性。
- **只读 / 受控写写法**：
    
    ```csharp
    public int Level => level;          // 表达式体，只有 get，外部只读（等价 { get { return level; } }）public int Level { get; }           // 只读自动属性，只能在构造函数里赋值public int Level { get; private set; } // 外部只读、类内部可写
    ```
    

##### 5. 关键细节 / 陷阱

- **set 里钳制的标准套路（本轮 bug 的正解）**：**先把 `value` 修正到合法范围，最后统一 `字段 = value` 落库。**
    
    ```csharp
    set{    if (value > 100) value = 100;    else if (value < 0) value = 0;   // 改 value，和上面对称    volume = value;                   // 最后统一把（钳制后的）value 写进字段}
    ```
    
    - ⚠ 易错：分支里改的必须是 **value（入参）**，不是字段；否则最后 `字段 = value` 会**覆盖掉钳制**（本轮就是分支里误写 `volume=0`、又被最后 `volume=value` 冲掉）。
- **“要加逻辑 → 不能用自动属性”**：本轮用行动答对（直接写完整版）。判据：需要在 set/get 里塞代码，就展开;不塞就用 `{get;set;}`。

##### 6. 应用速查（Unity 实践）

|需求|写法|
|---|---|
|外部只读、内部可改|`public int Hp { get; private set; }` 或 `public int Hp => hp;`|
|赋值时钳制范围|完整属性，set 里改 `value`，最后 `字段=value`|
|纯数据、无需逻辑|自动属性 `{ get; set; }`|
|Inspector 可调 + 代码封装|`[SerializeField] private int hp;`|

- **`[SerializeField] private` 优于 `public`**：
    - `public int hp;` → Inspector 可调，**但任何脚本也能乱改**（破坏封装）。
    - `[SerializeField] private int hp;` → **Inspector 可调 + 保持 private**（别的脚本改不了）。规范做法。
    - 破除误解：字段要在 Inspector 显示**不必** public，`[SerializeField]` 让 private 也能序列化/显示。（更细的序列化机制见 Unity“序列化”笔记）

##### 7. 踩过的错（错 → 正）

- 错：set 钳制分支里 `volume=0`（改字段）、最后 `volume=value` 覆盖钳制 → 正：分支里统一改 **`value`**，最后 `volume=value` 落库。
- 错（遗漏）：以为凡属性都能自动 `{get;set;}` → 正：**set 需要逻辑就不能用自动属性**，要展开成带字段的完整属性。

##### 0. 一句话速记

- **接口 = 能力契约**：只规定“**必须有哪些方法/属性**”，传统接口**无实现、无实例字段**。回答“**你能做什么**”。
- **抽象类 = 不能实例化的父类**：可有**现成实现 + 字段**，也可留 `abstract` 方法强制子类实现。回答“**你是什么**”。
- 最硬一条：**一个类只能继承 1 个抽象类（单继承），但能实现多个接口。**

##### 1. 核心表

|接口 interface|抽象类 abstract class|
|---|---|---|
|能否有实现|传统接口只声明、无实现|**能**（可给子类共用代码）|
|能否有实例字段|**不能**|**能**（如 `hp`）|
|一个类能有几个|**多个**（可叠加）|**1 个**（单继承）|
|回答的问题|能做什么（can-do）|是什么（is-a）|
|能否实例化|否|否（但可被继承后实例化子类）|

##### 2. 原理 / 机制（用例子锚，不背）

```csharp
// 抽象类：给出共用实现 + 强制子类填空
abstract class Character {
    public int hp = 100;                       // 可以有字段
    public void TakeDamage(int d) { hp -= d; } // 可以有现成实现（子类共用）
    public abstract void Move();               // 抽象方法：空的，强制子类实现
}

// 接口：只有契约，没有实现、没有字段
interface IAttackable {
    void Attack();   // 只声明，没方法体
}
```

- **抽象类**用于一组类**共享本质 + 共用代码**：Player/Enemy/NPC 本质都“是角色”，共享 hp、共享 TakeDamage → 写一遍、子类继承。
- **接口**用于给**本质不同**的类赋予**同一种能力**：Player、炮塔、陷阱本质完全不同、没法用一个共同父类装，但都“能攻击” → 各自实现 `IAttackable`。谁需要这能力谁实现，与它本来是什么无关。
- **为什么接口能挂多个、父类只能一个**：能力可**叠加**（一个东西可以同时能攻击、能移动、能被点击）；本质只有一个（父类名额宝贵）。

##### 4. 选型映射（必有）

|特征|用|为什么|
|---|---|---|
|一组类**是同一种东西**、共享本质 + 共用代码|抽象类|is-a，把共用实现写一遍继承|
|给**本质不同**的类赋予**同一能力**|接口|can-do，能力与本质无关|
|需要**多个**能力叠加|接口|可实现多个|
|需要**共用字段/现成方法**|抽象类|接口不能有实例字段/实现|

- **一句判据**：**抽象类回答“你是什么”（继承本质+共用代码，单继承）；接口回答“你能做什么”（赋予能力，可多实现）。**
- **常态**：一个类**既继承一个抽象类、又实现多个接口**：
    
    ```csharp
    class Player : Character, IAttackable, IMovable { }//             ↑唯一父类(本质)  ↑可叠加的能力(多个)
    ```
    

##### 5. 关键细节 / 陷阱

- 命名惯例：接口以 `I` 开头（`IList`/`IDictionary`/`IAttackable`）。
- 三硬区别记牢：**有无实现 / 有无字段 / 继承数量**。
- （版本演进：较新 C# 允许接口有默认实现等，主干先记“传统接口只声明”。）

|---|---|

##### 0. 一句话速记

- **struct = 值类型**（拷贝一整份数据）；**class = 引用类型**（拷贝地址、共享同一对象）。
- 这不是要背的规定，是从“**纯小数据当然按值拷贝 / 有身份当然共享引用**”推出来的。
- 选型：**纯数据、量小、拷来拷去无所谓 → struct；有身份、要被多处引用、不希望被拷 → class。**

##### 1. 核心表

|struct（值类型）|class（引用类型）|
|---|---|---|
|例子|`Position{ x,y,z }` 纯数据|`Player{ hp, 方法 }` 有身份|
|赋值 `b=a`|拷贝一整份数据，两份独立|拷贝地址，指同一对象|
|改一个影响另一个|不影响|影响（同一对象）|
|能否为 null|**不能**（它就是数据）|能|
|默认状态|全字段各自默认值（如 (0,0,0)）|值类型字段默认值、引用字段 null|
|自定义构造约束|写了**带参构造**必须给**所有字段**赋值|无此限制（漏赋的自动默认/null）|
|无参构造|不能自己写（老规则）；有语言内置的全默认值实例|没写任何构造时，编译器送一个**空的** public 无参构造|

##### 2. 原理 / 机制（从两个例子推四条区别）

**锚**：`struct Position{ float x,y,z }`（纯数据、量小、到处拷贝无所谓）、`class Player{ int hp; ... }`（有身份、要被多处引用、不希望被拷）。

从“**纯数据拷贝 vs 有身份共享**”这**一个锚**，推出一串区别：

1. **值/引用**：纯数据适合“拷贝一整份”→ 值类型（struct）；要被共享的实体适合“只传地址、大家指同一个”→ 引用类型（class）。
2. **赋值行为**：`Player b=a;` 改 `b.hp` 连带改 `a.hp`（同一对象）；`Position p2=p1;` 改 `p2.x` **不影响** `p1.x`（两份独立数据）。
3. **null**：class 可为 null（攥地址、可空着）；struct 不能为 null（它**直接就是数据本身**，没有“空着不指向”这个状态）。
4. **默认值**：struct 也有默认值（从“int 默认 0”类推 → `Position` 默认 `(0,0,0)`，每个字段取各自类型默认值）。

##### 5. 关键细节 / 陷阱（本篇的核心辨析都在这）

**A. 构造约束（结论 + 正确归因）**

- struct **不能自己写无参构造**（老规则）；能写**带参构造**，而**一旦写了带参构造，必须给所有字段显式赋值**，一个都不能漏。class 无此要求（漏赋的自动默认/null）。
- ⚠ **易滑归因（本轮反复滑，重点盯）**：这个强制**不是**因为“写了自定义构造 → 字段初始化机制失效、所以得补”。默认初始化机制**没被关掉**。正确说法是：**选了“自定义构造”这条路，语言就要求这条路对全字段负责**——是**语言的强制要求**，与“兜底在不在”无关。
    - 反例思路：若按“没兜底所以强制”那个错理由，会推出“class 也不该有 null 兜底”之类的错结论。

**B. 默认值到底是谁的功劳（两轮追问掰开的核心，别混）**

- **“字段变默认值(0/null)” = 默认初始化（内存层）的功劳，class/struct 都一样，与构造函数无关。**
- **构造函数只负责“new 时你想额外做的初始化逻辑”**，不是“给字段赋默认值的那只手”。
- **class 的无参构造**：没写任何构造时，编译器送一个**空的** public 无参构造（只为“能 new”，**不负责清零**——清零是默认初始化干的）。一旦你自己写了**任意**构造，编译器**不再**自动送无参构造 → `new Player()` 会编译不过（除非自己补一个无参的）。
- **struct 的“默认无参构造”**：更像一个**语言概念上的名字**（代表“给我一个全默认值的实例”），**不是一段真在赋值的代码**。`Position p;` / `new Position()` 拿到全默认值，靠的是值类型默认初始化，不是某段构造代码逐个赋值。

##### 4. 选型映射（必有）

|特征|用|为什么|
|---|---|---|
|纯数据、字段少、频繁创建/拷贝|struct|值类型、拷贝便宜、少堆分配|
|有身份、要被多处引用、共享同一份|class|引用类型、大家指同一个|
|不希望“各拿各的副本改半天没改到真正那个”|class|引用共享|
|需要 null 表示“空着/没有”|class|struct 不能为 null|

- 判据一句话：**纯小数据 → struct；有身份要共享 → class。** 其余区别都从这一条推。

##### 7. 踩过的错（错 → 正）

- 错：“struct 自定义构造必须赋全”是因为“写了构造→字段初始化机制失效” → 正：因为**语言强制“自定义构造对全字段负责”**，默认初始化机制并没失效。
- 错（倾向）：把“字段拿默认值”当成构造函数的功劳 → 正：**默认值来自默认初始化（内存层），与构造函数无关**；构造函数只做“额外初始化逻辑”。

##### 0. 一句话速记

执行顺序：**Awake → OnEnable → Start →（每帧）FixedUpdate×N → Update → LateUpdate**。**FixedUpdate 在 Update 之前**，且一帧执行 **0~N 次**（按固定步长、由累加器驱动）。**全场 Awake 全跑完，才进任何一个 Start**——所以"依赖别人初始化好"的操作放 Start。

---

##### 1. 回调顺序与职责

|回调|何时|干什么|次数|
|---|---|---|---|
|`Awake`|对象创建时（哪怕脚本 disabled）|最优先的自我初始化（缓存自己的引用）|1 次|
|`OnEnable`|每次对象/脚本被启用|启用时要做的（如 `+=` 订阅事件）|多次|
|`Start`|第一次 Update 前（要求脚本 enabled）|依赖别人已初始化好的初始化|1 次|
|`FixedUpdate`|按固定物理步长（默认 0.02s）|物理逻辑（AddForce 等）|**一帧 0~N 次**|
|`Update`|每渲染帧|主逻辑、输入检测|每帧 1 次|
|`LateUpdate`|Update 之后|跟随摄像机（等被跟随物体这帧移动完再动，避穿模）|每帧 1 次|
|`OnDisable`/`OnDestroy`|禁用 / 销毁时|释放、`-=` 取消订阅|—|

> 铁律：`OnEnable` 里 `+=` 订阅 / `OnDisable`（或 OnDestroy）里 `-=` 取消，成对，防失效监听器（lapsed listener）内存泄漏。

---

##### 2. 为什么物理放 FixedUpdate、输入放 Update

- **物理放 FixedUpdate**：Update 每帧一次、帧率会飘（60/144/30 帧），若在 Update 里 AddForce，加力次数跟着帧率变、物理不稳定、联机不同步。FixedUpdate 按固定步长，**1 秒执行次数与帧率无关**，物理稳定。
- **输入 `GetKeyDown` 放 Update**：`GetKeyDown` 的"按下"信号**按渲染帧发放**，只有 Update 同频。放 FixedUpdate 会漏读（该帧 fix 跑 0 次→信号丢）或重读（跑多次→触发多下）。

---

##### 3. FixedUpdate 一帧 0~N 次 + 累加器

引擎有个**时间累加器**：

- 每渲染帧把这帧耗时（deltaTime）加进累加器。
- 攒够 0.02 → 跑一次 FixedUpdate，累加器减 0.02；还够就再跑…直到不够，停。
- 没攒够 → 这帧 0 次 FixedUpdate。
- 跑完该跑的 fix，才轮到 Update。

**后果**：这帧渲染卡了（耗 0.05s）→ 补跑 3 次 fix 再跑 1 次 Update；这帧很快（0.008s，没攒够 0.02）→ 0 次 fix。 **高帧率不是"永不执行 fix"**，是"每攒够 0.02 执行一次"，平均每秒恒定 50 次（1÷0.02）。

---

##### 4. 跨对象时序（高频坑）

**铁律**：**所有对象的 Awake 全部跑完，才开始跑任何一个对象的 Start。**（不是每个对象各自 Awake→Start，是全场 Awake 先于全场 Start。）

- 所以"读另一个对象在 Awake 里准备好的东西"（如读单例）→ 放 **Start**，保证对方 Awake 已跑完。放 Awake 会碰上"两对象 Awake 谁先谁后无保证"→ 可能读到 null 崩溃（且时好时坏、极难查）。

⚠ **边界**："全场 Awake 先于全场 Start"**只对同一批一起进场景的对象成立**（场景加载时就摆好的、或同帧一起 Instantiate 的）。**运行中途单独 Instantiate 的对象**：只保证它自己内部 Awake→OnEnable→Start 顺序，**不保证它和场景里其他对象的相对时序**（别的对象早跑完 Start 在 Update 循环里了）。别把铁律错记成"任何时候 Awake 都先于任何 Start"。

---

|需求|放哪|
|---|---|
|缓存自己的组件引用|Awake|
|读别的对象/单例已初始化好的东西|Start|
|订阅 / 取消订阅事件|OnEnable `+=` / OnDisable（或 OnDestroy）`-=`|
|物理（AddForce、Rigidbody 操作）|FixedUpdate|
|输入检测（GetKeyDown）、主逻辑|Update|

##### ★ 本轮摸底实录（误区 / 纠正 + 遗漏）

> 这一块是**这次摸底当场**暴露的东西：我答错/答反了什么、漏了什么。下面是"知识该长的样子"，这里是"我当时卡在哪"。复习时先扫这块看自己的坑，再看下面的结构。

**答得好的地方（先记对的）**：

- "为什么运行时要动态 Instantiate、不提前全摆完"——理解到位（运动伴随新对象生成，不可能提前摆完）。

**误区 / 纠正（当场答错、答反或混淆的）：**

- 表述歧义（Claude 先误判、后收回）：说"Prefab 是提前设好参数的 GameObject"。 **澄清：Prefab = 图纸（硬盘上 .prefab 资源，不在场景不运行）；实例 = 照图纸造的 GameObject（在场景、渲染、跑逻辑）。用户本意是"实例产物是绑定 .prefab 的 GameObject"，本意正确。**
- 误区（真误区，非生疏）：以为 runtime 在代码里改 Prefab 资产，已实例化的对象会跟着更新。 **纠正：不会。实例出生即与图纸脱钩，是内存中独立对象，收不到图纸改动通知。（把"编辑器期同步"误推到了 runtime。）**
- 概念混淆：以为 ScriptableObject 能做"给敌人加受击闪红"。 **纠正：SO = 纯数据容器，不进场景、无 Transform、不渲染、不跑 Update，做不了运行时行为。加行为改 Prefab、改数值用 SO、二者配合非替代。**

**遗漏 / 初次接触：**

- Variant（预制体变体）——没用过。补：Variant = 继承（父 Prefab=基类，Variant=子类，override 个别项、其余跟随父，改父传子）。（见 §3）
- 实例属性 override（"改图纸后有 1 个实例不跟着变"= 那项被单独 override 过，蓝色竖线，Revert 恢复）。（见 §4）

**本轮判定**：核心理解到位；出现 2 个非生疏项（runtime 同步误区、SO 混淆），性质是"把编辑器直觉误推到 runtime""把物体模板与纯数据容器混为一类"，非无根缺口，一经锚定即通——区别于弧度/坐标衔接那种需专项重建的硬缺口。

##### 0. 一句话速记

**Prefab = 类（图纸），实例 = 对象（照图纸造的 GameObject）。`Instantiate` = new 一个实例。** 编辑器期改图纸→所有实例跟着变；**运行时已实例化的对象与图纸脱钩，改图纸没用**。Variant = 继承（改父传子，子 override 的部分保留）。

---

##### 1. Prefab vs GameObject（核心，面试常问）

|Prefab|场景里的 GameObject|
|---|---|---|
|是什么|一份存在硬盘的**模板/图纸**（`.prefab` 文件，在 Project 窗口）|照图纸造出来的一个**实例**（在场景里）|
|在不在游戏世界|不在，不运行|在，会被渲染、跑逻辑|
|C# 类比|**类**|**对象/实例**|

`Instantiate(prefab)` = **new 一个实例**。一份 Prefab 能 Instantiate 出成百上千个 GameObject（一个类 new 无数对象）。

> 坑：菜单 `3D Object → Cube` 拖出来的**不是 Prefab**（是内置一次性组装，无 `.prefab` 文件），除非你自己拖进 Project 存成 Prefab。

---

##### 2. 为什么运行时要动态 Instantiate

运动伴随新对象不断生成（子弹、敌人、掉落物，数量运行时才知道），**不可能提前把所有对象一次性摆进场景**。图纸放着不占世界，要几个造几个。

---

##### 3. Variant（预制体变体）= 继承

一批对象**大部分相同、少数字段不同**时用。

- 父 Prefab = 基类；Variant = 子类。
- Variant **继承**父的一切，只 **override** 它要改的那几项（如血量），其余**跟随父**。
- 改父 Prefab（如加"受击闪红"）→ **所有 Variant 自动继承**；各 Variant 自己 override 的项（血量/速度/模型）**保留不受影响**。

**用途**：敌人分级（普通/精英/Boss）、同一按钮的不同配色版、同种道具的不同稀有度。 **创建**：选中 Prefab 右键 `Create → Prefab Variant`；或把改过的实例拖回 Project 窗口、弹窗选 **Prefab Variant**（选 Original 就是另起一份没关系的图纸）。

---

##### 4. 实例属性 override（"改图纸有个别实例不变"的机制）

场景里每个实例的每个属性有两种状态：

- **跟随图纸（默认）**：没动过，改图纸它跟着变。
- **被 override**：在**这个实例身上**单独改过这个属性（如把这一个敌人血量改成 500）→ 与图纸**脱钩**，此后改图纸它不跟着变。Inspector 里该属性旁有**蓝色竖线 + 加粗**。想恢复跟随 → 该属性右键 **Revert**。

> 两种 override 同一内核：Variant 的 override = 子图纸盖父图纸；实例的 override = 成品盖图纸。都是"覆写的归自己、没覆写的跟随上游"，同 C# 继承 override 心智模型。

---

##### 5. 关键陷阱

###### 陷阱：runtime 改 Prefab，已实例化对象不更新 ★高频坑★

- **编辑器期**改 Prefab → 所有实例（蓝色链接还在的）自动跟着变（编辑器同步便利）。
- **运行时（Play）**：那些实例已是内存里独立的对象，**出生后各过各的**。代码里动"图纸"资产，内存里已造好的实例**收不到通知、不会变**（且运行时改 Prefab 资产本身不是正常做法）。

**运行时想让已存在的实例全体变化** → 不是改图纸，而是：拿到实例引用**逐个操作**，或用**事件广播**让它们自己响应。

###### 混淆：Prefab vs ScriptableObject

- **改行为 / 换特效 / 加组件 → 改 Prefab**（那是物体和它的逻辑）。
- **改数值 / 配置 / 一张表 → 用 ScriptableObject**（纯数据，不进场景、无 Transform、不跑 Update）。
- 常配合：Prefab 挂脚本、脚本引用一个 SO 读数值。**非互相替代。**

---

##### 6. 应用速查

|需求|怎么做|
|---|---|
|运行时生成对象|`Instantiate(prefab)`|
|一批对象大部分相同、少数不同|做成 Prefab Variant（改父传子）|
|改了 Prefab 发现某实例没变|该实例那项被 override 了（蓝线），Revert 恢复跟随|
|运行时让已存在实例全体变化|拿引用逐个操作 / 事件广播，**别改图纸**|
|存一批可调数值/配置|ScriptableObject（不是 Prefab）|
|给对象加行为/特效|改 Prefab（不是 SO）|

##### 0. 一句话速记

四种坐标：**世界**（相对世界原点的绝对位置）、**本地**（相对父 Transform 的偏移）、**屏幕**（左下原点、像素）、**视口**（左下(0,0)~右上(1,1)、0~1 比例、不依赖分辨率）。转换记两个高频：**UI 跟随 3D 物体 = 世界→屏幕（WorldToScreenPoint）**；**鼠标点选 3D 物体 = 屏幕→世界射线（ScreenPointToRay + Raycast）**。

---

##### 1. 四种坐标是什么

|坐标|相对谁|原点/范围|单位|
|---|---|---|---|
|世界 World|世界原点 (0,0,0)|—|世界单位|
|本地 Local|**父 Transform**（位+旋+缩）|相对父的偏移|世界单位（受父缩放影响）|
|屏幕 Screen|屏幕|**左下 (0,0)**，右上 (Screen.width, Screen.height)|**像素**|
|视口 Viewport|屏幕|**左下 (0,0)，右上 (1,1)**，正中 (0.5,0.5)|0~1 比例|

- **`position` vs `localPosition`**：无父时两者数值相等；有父时 `localPosition` 是相对父偏移、`position` 是父变换叠加后的世界结果。
- **视口 vs 屏幕**：同一东西换刻度——视口 0~1（不依赖分辨率），屏幕像素（依赖分辨率）。

---

##### 2. 视口坐标用在哪

特征永远是"要相对比例、不要管分辨率"。典型：

- **摄像机 Viewport Rect**（最正统）：分屏（玩家1 `(0,0.5,1,0.5)` 上半、玩家2 `(0,0,1,0.5)` 下半）、小地图（`(0.8,0.8,0.2,0.2)` 右上角）。
- **判断物体在不在屏幕内**：`WorldToViewportPoint`，x、y 都在 0~1（且 z>0 在相机前）→ 在屏幕内。
- 按屏幕比例定位（非 UI 时；UI 有 anchor 更常用）。

---

##### 3. 转换方向感（重头，面试爱问）

**场景 A：UI 血条跟随 3D 玩家**

- 玩家有世界坐标，血条是屏幕 UI，要血条摆到玩家头顶的屏幕位置。
- **世界 → 屏幕**：`Camera.WorldToScreenPoint(玩家世界坐标)` 拿到"头顶在屏幕的哪个像素"，把 UI 摆过去。
- （血条、伤害数字、头顶名字全靠这个。别用视口——视口是比例，摆 UI 还差一步换算。）

**场景 B：鼠标点选 3D 物体**

- 鼠标给的是**屏幕坐标**（像素）。
- **屏幕 → 世界射线**：`Camera.ScreenPointToRay(鼠标屏幕坐标)` 把"屏幕上这个像素"翻译成"从摄像机射进 3D 世界的一条射线" → `Physics.Raycast` 检测射线撞到哪个碰撞体 → 命中哪个物体。
- ⚠ 全程和"本地坐标"无关。本地是父子相对关系，别往这儿套。

---

##### 4. 关键细节 / 陷阱

- **本地坐标 ≠ "相对父中心点"**：是相对父 Transform（位+旋+缩）的偏移。父旋转/缩放，子的世界位置跟着转、跟着缩。
- **别被"本地/世界"术语混**：从屏幕射进 3D 世界，目标空间是**世界**（射线在世界飞），不是本地。
- **UI 跟随用屏幕不是视口**：视口 0~1 是比例，UI 最终按像素摆位。

##### 5. 应用速查

|需求|用哪个转换|
|---|---|

**误区 / 纠正（当场答错或答反的）：**

- 误区：把"判断前后 + 左右"整个记给了叉乘。 **纠正：前后（同向/反向）= 点乘看符号；左右（哪一侧）= 叉乘。分水岭是"点乘出数、叉乘出向量"。**
- 误区：判断"视线是否正对墙"（视线 vs 墙面法线）→ 用了叉乘看 y=0。 **纠正：用点乘。"正对"是方向一致性（同向/垂直），归点乘。被"法线"一词带跑了——法线是已知输入、不是要求它。**
- 误区（对适用边界）：以为"手性会变、所以左右符号每次要实测"。 **纠正：Unity 手性固定（左手系）。要实测是为省"参数顺序 / 看哪个分量 / forward 定义"记反的风险，不是手性不固定。**

**遗漏 / 经追问补上的（本轮往边界钻问出来的）：**

- 追问①两个"=0"边界：点乘=0→垂直（正左/右线，cos=0）；叉乘=0→共线（正前/后线，sin=0）。两盲区互补。（见 §4）
- 追问②Unity 手性是否固定 → 固定，左手系。（见 §6）
- 追问③Unity 实际帧左右符号 → `Cross(forward,toEnemy).y>0 ⟺ 敌人在右`，与 2D 俯视草图符号相反是坐标约定不同。（见 §6）

**本轮判定**：**本组唯一"真需练"点**（非纯生疏）——机制层已锚住（点乘出数/叉乘出向量、第2题求法线推对证明），缺的是"问题特征词→选哪个工具"的映射（选型层未绑牢）。归待强化项，与弧度/坐标衔接同类但更轻（那两者机制层塌需重建，这个仅补映射即可）。几何理解本身到位（=0 边界追问显示），唯一缺口精确在"特征词触发哪个工具"的条件反射。

##### 0. 一句话速记

- **点乘出一个数** → 看符号，管**同向/反向**（前后、夹角、垂不垂直）。
- **叉乘出一个向量** → 管**垂直方向**（左右、法线、垂直轴）。
- 分水岭：**结果是数还是向量**。选型时先认这个。

---

##### 1. 核心分工表

|点乘 Dot|叉乘 Cross|
|---|---|---|
|结果|一个**数**（标量）|一个**向量**|
|公式(3D)|`Ax·Bx + Ay·By + Az·Bz`|`(Ay·Bz−Az·By, Az·Bx−Ax·Bz, Ax·By−Ay·Bx)`|
|几何|`=|A|
|管什么|同向/反向（**前后**、夹角、是否垂直）|垂直方向/哪一侧（**左右**、法线）|
|典型用途|敌人在前还是后、两向量夹角、判垂直|敌人在左还是右、求三角形法线、求垂直轴|

> 叉乘的公式就是 `Vector3.Cross(A, B)` 的源码逐分量展开，Unity 里一模一样。

---

##### 2. 点乘的几何意义

`Dot(A,B) = |A||B|cosθ`

- 几何上 = **B 在 A 方向上的投影长度**（`|B|cosθ`）**× |A|**。
- 符号完全跟着 cos 走（因为 |A|、|B| 恒正）：

|点乘|夹角|含义|
|---|---|---|
|**> 0**|< 90°|大致同向（投影与 A 同向）→ 敌人在**前**|
|**= 0**|90°|垂直（投影为 0）|
|**< 0**|> 90°|大致反向（投影反向）→ 敌人在**后**|

**用途落地**：判断"敌人在我前还是后" → `Dot(transform.forward, 敌人位置 − 我位置)`，看符号。

---

##### 3. 叉乘的几何意义

`Cross(A,B) = (Ay·Bz−Az·By, Az·Bx−Ax·Bz, Ax·By−Ay·Bx)`

- **方向**：垂直于 A、B 张成的平面 = 那个平面的**法线**；按**左手定则**（Unity 是左手系）。
- **长度**：`|A||B|sinθ` = **A、B 张成的平行四边形面积**。
- **= 0（零向量）**：A、B 共线（平行，0° 或 180°），面积塌成 0。

**用途落地**：

- 求三角形法线 → **两条边向量叉乘**（小车 mesh 的 `RecalculateNormals` 背后就是这个）。
- 判断敌人在左还是右 → `Cross(forward, toEnemy)` 看分量符号（见第 6 节，符号要实测钉死）。

---

##### 4. 两个「= 0」互为镜像（精髓）

|前后 · 点乘|左右 · 叉乘|
|---|---|---|
|= 0 意味着|**正左/正右**（垂直，90°）|**正前/正后**（共线，0°/180°）|
|落在哪条线|前后的**分界线**|左右的**分界线**|
|背后三角函数|cos = 0|sin = 0|

> 一个判断的盲区（它的 =0 那条线）正好是另一个判断最清晰的地方。所以实战常**两个一起用**：点乘定前后 + 叉乘定左右。

---

##### 5. 选型映射（看到什么词 → 用哪个）

|关键词|→ 本质|→ 用哪个|
|---|---|---|
|正对 / 同向 / 反向 / 前后 / 夹角 / 垂不垂直|方向一致性|**点乘**（看数的符号/大小）|
|哪一侧 / 左右 / 法线 / 垂直轴 / 转向|求垂直方向|**叉乘**（拿那个向量/看分量符号）|

**两个易混陷阱**：

- **「求法线」用叉乘；「拿一条已知向量去比方向对不对齐」用点乘。** 看到"法线"别条件反射叉乘——先分清是**要算出**法线，还是**已知**法线拿来比方向。
    - 例：判断"视线是否正对墙"（视线 vs 墙面法线）→ 用**点乘**（正对 = 方向一致性）。`Dot(视线, 墙法线)` 绝对值大 → 接近平行 → 正对；接近 0 → 垂直 → 擦过没正对。**法线在这里是已知输入，不是要求它。**

##### 6. 手性 & 左右符号（Unity 实际帧，重点）

**Unity 世界坐标手性固定 —— 左手系**：`+X 右`、`+Y 上`、`+Z 前（进屏幕）`。不随场景变。

> 对比：数学教材 / OpenGL / Blender 多为右手系（+Z 朝屏幕外）。这是数学书上的叉乘搬到 Unity"感觉方向反了"的根源。

**Unity 真实帧里判左右的标准答案**： 角色 `forward = +Z`、右手边 = `+X` 时——

```
Cross(forward, 指向敌人).y > 0  ⟺  敌人在你右边   （y < 0 = 左）
```

验算：`Cross((0,0,1),(1,0,0)) = (0, 1, 0)`，y = +1 > 0 → 右。✓

**为什么仍要"实测一次"钉死符号**（不是因为手性会变）： 方向由左手定则**定死、可推**，但"y>0 到底是左是右"还依赖三件容易记反的事：

1. **参数顺序**：`Cross(forward,toTarget)` vs `Cross(toTarget,forward)` —— 反了结果整个反向（`a×b = −(b×a)`），符号翻。
2. **看哪个分量**：角色在地面（XZ 平面）→ 看 `.y`；2D 游戏（XY 平面）→ 看 `.z`。取决于你的游戏在哪个平面。
3. **forward 与"我的右"怎么定义**。

> 结论：能纯靠推，但要同时把"左手定则 + 参数顺序 + 哪个平面 + forward 朝向"四项都摆对，错一个符号就反。**实测一次**（拿一个已知在右的物体，打印 `Cross(forward,toEnemy).y` 看正负）绕开这四步全对的风险，一步到位。

**与 2D 俯视草图符号相反不是矛盾**：那种"屏幕向上 = +y"的 2D 约定里，右侧对应的是**负**号；坐标约定不同而已。**以 Unity 实际帧为准。**

> 对照：**点乘的前后（cos 符号）不依赖以上任何一项**，手性、参数顺序都不影响 → 无需实测。

**误区 / 纠正（当场答错或答轻的）：**

- 说轻：以为不乘 Δt "只是会不正常地快"。 **纠正：真问题不是"快"，是"快慢取决于帧率、跨机器不一致"（60/144/30 帧速度全不同、联机不同步）。**

**当场亮点（值得记的好习惯）**：不确定"平方对不对"时，主动去 Unity **实测**，发现是匀速——这个实测结果反而成了推翻错误直觉的证据（Δt 每帧常数 → Δt² 也常数 → 每帧加固定量 = 匀速）。"不确定就实测"是好动作，继续保持。

**遗漏**：本点无明显遗漏，主干（deltaTime 是什么、为什么乘）理解到位，用物理直觉（距离公式的时间）自主抓对本质。

##### 0. 一句话速记

`Time.deltaTime` = 上一帧到这一帧过了多少秒。移动/旋转乘它，是把 **"每秒的量" 换算成 "这一帧的量"**，好让速度**不受帧率影响**。逐帧累加里 **Δt 只该乘一次**。

---

##### 1. 核心表

|含义|
|---|---|
|`Time.deltaTime`|两帧之间的间隔时间（秒）。60 帧≈0.0167s，30 帧≈0.0333s，144 帧≈0.0069s|
|为什么乘|`speed` 是"每秒移动量" → 乘 Δt 得"这一帧移动量"|
|不乘的后果|变成"每帧固定移动 speed" → 实际速度**跟着帧率走**，跨机器不一致|

---

##### 2. 原理：为什么乘了就"帧率无关"（带推导）

`transform.position += forward * speed * Time.deltaTime;`

- **不乘**：每帧动固定的 `speed`。60 帧→一秒动 `speed×60`；144 帧→`speed×144`；30 帧→`speed×30`。**同一 speed，高帧率快、低帧率慢，换台电脑手感就崩，联机不同步。**
- **乘了**：
    - 60 帧：每帧 `speed×0.0167`，一秒 60 帧 → `speed×0.0167×60 = speed×1`
    - 144 帧：每帧 `speed×0.0069`，一秒 144 帧 → `speed×0.0069×144 = speed×1`
    - **帧率高→单帧 Δt 小→每帧动得少但帧多；帧率低→Δt 大→每帧动得多但帧少。一乘一除正好抵消 → 每秒总位移恒定 = speed，与帧率无关。**

**乘 Δt 的全部意义**：把"每帧移动"换算成"每秒移动"，让速度跨机器一致。

---

##### 3. 精髓：和 FixedUpdate 同源

deltaTime 的思想 = **拿固定的真实时间，去对冲会飘的帧率**。这和 FixedUpdate"1 秒执行次数与帧率无关"是**同一个思想**：

- `Time.deltaTime`：在 Update 里**手动**做这件事。
- `FixedUpdate`：引擎在物理层**自动**做这件事。

一个道理，两处应用。

---

##### 4. 关键陷阱：匀加速不是"Δt 平方"（真误区，我踩过）

**踩坑现象**：想做匀加速，在 Update 里写 `position += forward * Δt * Δt`，结果是**匀速**。

**为什么是匀速**：稳定 60 帧时 `Δt≈0.0167` 是**常数** → `Δt²` 也是**常数** → 每帧加一个固定量 = **匀速**。加速根本没发生（只是把速度改小了）。

**根子**：`s = ½at²` 里的 `t` 是**从运动开始到现在的累计总时间**，不是"一帧的 Δt"。把解析公式里的累计 `t` 直接换成帧间隔 `Δt` 搬进代码 —— **同名不同义，搬错了。**

**正确写法（加速靠"速度变量自己累积"，不靠 Δt 加次方）**：

```csharp
float speed = 0f;    // 当前速度，类字段，跨帧保留
float a = 9.8f;      // 加速度

void Update()
{
    speed += a * Time.deltaTime;                              // 速度每帧涨一点 v = v + a·Δt
    transform.position += Vector3.forward * speed * Time.deltaTime;  // 用当前速度移动，和匀速同写法
}
```

- `speed += a*Δt`：速度**自己累积**，跑得越久越大 —— 加速**在这里**发生。
- `position += forward*speed*Δt`：和匀速移动**一模一样**的写法，只是 speed 每帧在变大。

---

##### 5. 关键细节 / 铁律

> **逐帧累加运动 = 当前速度 × Δt（Δt 只乘一次）。** 变化的运动（加速/减速）靠"速度变量随时间自己变"，**不靠给 Δt 加次方**。`½at²` 是描述**总量**的解析公式，不是逐帧累加的写法。

**最快自查**：逐帧累加里 Δt 正常只出现**一次**（率 × 一帧时间）。出现两次（Δt²）或一次都没有 → 大概率把解析公式硬搬进循环了。

---

##### 6. 踩过的错（错 → 正）

- 错：不乘 Δt "只是会不正常地快" **正：真问题不是"快"，是"快慢取决于帧率、跨机器不一致"（60/144/30 帧速度全不同、联机不同步）。**
- 错：匀加速 → 在 Update 里写 `position += forward * Δt * Δt`（以为"加速 = Δt 平方"） **正：加速靠速度变量累积（`speed += a*Δt`），Δt 只乘一次。根子：`½at²` 的累计 t 误当成帧间隔 Δt。**

> 归类（错误属哪类）：这属 **"解析式 ↔ 逐帧递推" 的语义没对齐** —— 解析公式描述总量、逐帧代码累加增量，两者的 t 同名不同义。以后遇到"把一个随时间变化的量写进 Update"，先问：我这一帧加的是不是"率 × Δt"？

##### ★ 本轮摸底实录（误区 / 纠正 + 遗漏）

- 特性名忘：知道"private + 加特性"能实现"外部不可改 + Inspector 可调"，但特性名忘了。 **补：`[SerializeField]`。**（知道有此物、名字忘 = 生疏非缺口。）

##### 0. 一句话速记

**"能不能在 Inspector 调" 由「序列化」决定，不由 public/private 决定。** 访问权限（public/private）和 序列化/显示 是**两个独立开关**。`[SerializeField]` 和 `[HideInInspector]` 就是单独拨第二个开关、不动第一个。

---

##### 1. 核心表：两个独立开关的四种组合

|想要的效果|访问权限|序列化/显示|写法|
|---|---|---|---|
|外部可改 + Inspector 可调|public|显示|`public int hp;`（默认）|
|**外部不可改 + Inspector 可调**|private|显示|`[SerializeField] private int hp;` ✅推荐|
|外部可改 + Inspector 隐藏|public|隐藏|`[HideInInspector] public int hp;`|
|外部不可改 + Inspector 隐藏|private|隐藏|`private int hp;`（默认）|

> 关键：public/private 管 **"别的脚本能不能访问"**（C# 访问权限）；序列化管 **"Unity 存不存、显不显示"**。两者独立，四种组合都能配。

---

##### 2. 原理：Inspector 显示的本质是"被序列化的字段"

因果链：

```
Unity 用【反射】扫描脚本上有哪些字段
  → 判断每个字段【符不符合序列化条件】
    → 符合的：存进场景/预制体文件，并显示在 Inspector
```

- **反射** = Unity "发现字段"的手段。
- **序列化** = "这个字段的值能被保存/显示"的真正机制。← Inspector 显示的根本原因。
- `public` 字段**默认符合序列化条件**，所以 public 会显示 —— 但这只是"符合序列化"的一种情况，**不是根本原因**。根本原因是序列化。

---

##### 3. 两个特性（正好相反的一对）

- **`[SerializeField] private int hp;`** —— private 管住外部访问（别的脚本不能改），`[SerializeField]` 单独让 Unity 序列化它 → Inspector 可调，但代码层面私有。**Unity 推荐做法**（比全 public 好：public 同时开两扇门破坏封装；这个只开"Inspector 可调"那扇）。
- **`[HideInInspector] public float speed;`** —— 字段 public（别的脚本要能访问），但不想它出现在 Inspector（怕手滑改、或由代码控制）。→ "public 但对 Inspector 隐身"。

---

##### 4. 关键陷阱

###### 陷阱 1：序列化的值，盖过代码里的初始值 ★高频坑★

`[SerializeField] private int hp = 100;`，若在 Inspector 里拖成了 500 → **运行时初始值是 500，不是 100。**

机制（顺序）：

```
代码的 = 100 先给个底
  → Unity 用序列化存下来的 500 盖上去（存在场景/预制体文件里）
    → 运行时看到 500
```

**要命之处**：代码里写着 `=100`，你以为初始是 100，游戏里却是 500，回头翻代码找不到 500（它藏在场景文件里）。 **记死**：字段一旦序列化，代码里的初始值只是"**没在 Inspector 动过时的兜底**"；只要 Inspector 动过，**以 Inspector 为准**。

**想让代码永远说了算 → 在 `Start`/`Awake` 里赋值**：

```csharp
private int hp;   // 不 [SerializeField],不暴露也不序列化
void Start(){ hp = 100; }   // 代码说了算,Inspector 影响不到
```

原理（顺着执行顺序）：`Start`/`Awake` 在**对象加载之后**执行。时间线 = Unity 先用序列化值 500 盖字段 → 再跑 `Start` 里 `hp=100` 盖回去 → 后写赢，最终 100。**用"执行顺序"压过"序列化"。**

**⚠ 两个边界，别用过头**：

1. **别 `[SerializeField]` 暴露 + `Start` 里写死同一个字段** —— 那 Inspector 那个框就是摆设（调了被 Start 盖掉），还误导人。**决定权给谁就只留谁**：代码写死→`private` 不暴露；想 Inspector 调→`[SerializeField]` 且别在 Start 再赋值。别两个都占。
2. **判据 = 这个值是"设计参数"还是"运行时状态"**：
    - **设计参数**（策划要调的：最大血量、移动速度、伤害）→ 就该 `[SerializeField]` 暴露，**恰恰不该**在 Start 写死（写死策划就调不了了）。
    - **运行时状态**（当前血量、当前分数）→ 才该代码控制初始值。

**成熟写法（最常见）：暴露参数 + Start 里用它初始化状态**：

```csharp
[SerializeField] private int maxHp = 100;   // 设计参数,Inspector 可调
private int currentHp;                        // 运行时状态,不暴露
void Start(){ currentHp = maxHp; }            // 用可调的最大值初始化当前值
```

两字段各司其职：`maxHp` 给策划调，`currentHp` 由代码从 `maxHp` 初始化，谁都不越界。

###### 陷阱 2：运行中改 Inspector，一停就回滚 ★高频坑★

- 运行**前**改 Inspector → 存进文件，**永久生效**。
- 运行**中**改 Inspector → **当场立刻生效，但一退出 Play 模式全部丢失**、变回运行前的值。

**翻车场景**：Play 模式下辛苦调了一堆参数，觉得好了，一点停止——全没了。 **正确做法**：非运行状态下调；或运行时记下数值、停止后再填回去。

---

##### 5. 应用速查

|需求|怎么写|
|---|---|
|数值想在 Inspector 调，但不想被别的脚本乱改|`[SerializeField] private`|
|public 字段（要被别的脚本访问）但不想在 Inspector 露|`[HideInInspector] public`|
|纯内部字段，既不暴露也不给外部|`private`（默认）|

|既想策划能调、又想代码初始化当前值|`[SerializeField] private maxHp` + `Start` 里 `currentHp = maxHp`|
|Play 模式下调好的参数想保留|记下来，停止后填回；别指望自动保存|

#### Transform 层级操作 —— 复习笔记（完整版）

##### ★ 本轮摸底实录（误区 / 纠正 + 遗漏）

##### 0. 一句话速记

父子关系锁定的是 **"子相对父"的关系**：父动，子的 **localPosition（相对父偏移）不变**，**world（世界 transform）跟着父一起变**。子的世界变换 = **父的世界变换（位/旋/缩）叠加到子的 local 值上**。

---

##### 1. 核心：父子关系一旦建立，子跟随父的什么

|父发生|子的表现|
|---|---|
|父移动|子跟着平移（world 位置变，local 不变）|
|父旋转|子跟着转向（连带绕父转，world 旋转/位置变，local 不变）|
|父缩放|子跟着缩放（子的世界大小/离父距离被放缩，local 不变）|

**核心一句**：父子关系**锁定"子相对父"不变**（local 不变），让子**跟随父的整个变换**（world 变）。

> ⚠ 大多数人第一反应答反：以为拖成子物体后 localPosition 会变。**不会**——变的是 world，不变的是 local。

---

##### 2. 原理：子的世界变换怎么来的

```
子的世界变换 = 父的世界变换（位置 + 旋转 + 缩放）叠加到 子的 local 值上
```

localPosition 是"**父坐标系里的偏移**"，要依次经过：

- 父的**缩放** → 放缩这个偏移（父放大 2 倍，子的偏移距离 ×2）
- 父的**旋转** → 转这个偏移的方向
- 父的**位置** → 平移

才得到世界结果。所以父一动，"乘数/加数"变，world 输出跟着变，而你输入的 local 没动 —— 这就是"local 不变、world 变"的原因。

**例**：B 挂在 A 下，A 世界缩放 `(2,2,2)`，B 的 localPosition `(1,0,0)` → B 离 A 世界距离 = `1 × 2 = 2`（父缩放放缩了子的偏移）。

---

##### 3. 改父子关系：`SetParent`

```csharp
B.transform.SetParent(A.transform);        // 把 B 挂到 A 下面
B.transform.SetParent(null);                // 传 null = 摘出来,挂回场景根层("断绝父子")
```

**第二参数 `worldPositionStays`（挂上去位置跳不跳的原因）**：

```csharp
B.transform.SetParent(A.transform, true);   // 默认:保持 B 世界位置不变(Unity 自动重算 local 抵消)
B.transform.SetParent(A.transform, false);  // 保持 local 数值不变 → B 会跳到新父坐标系下那个偏移处
```

- `true`（默认）：换父后 **B 在世界待的地方不动**。
- `false`：**保持 localPosition 数值**，于是 B "啪"地跳走。

> 老写法 `B.transform.parent = A.transform` 等价于 `SetParent(..., true)`，但没法传参数 → 现在推荐用 `SetParent`。

---

##### 4. position vs localPosition（从层级角度）

- **无父物体**（在场景根层）：`position` 和 `localPosition` **数值相等**（"相对父"的父就是世界原点）。
- **有父物体**：两者不同 —— `localPosition` 是相对父的偏移，`position` 是父变换叠加后的世界结果。

**高频坑：改 `position` 和改 `localPosition` 效果不同**

- `子.position = (0,0,0)` → 跑到**世界原点**。
- `子.localPosition = (0,0,0)` → 跑到**父物体所在位置**（相对父偏移为 0）。
- 别以为都是"归零"：一个归到世界原点，一个归到父身上。

---

##### 5. 关键细节 / 陷阱

- **非均匀缩放的父 → 子会变形**：父在不同轴缩放不同（如 X×2、Y×1），子若又有旋转，世界形状被拉歪（skew/切变）。知道有这回事，非均匀缩放 + 旋转的父子结构要当心。
- **`SetParent` 位置跳** → 十有八九是 `worldPositionStays` 参数（默认 true 世界不动；传 false 保 local 数值会跳）。

---

##### 6. 应用速查

|需求|怎么做|
|---|---|
|让 B 跟着 A 一起动（位/旋/缩）|把 B 设为 A 的子物体（`SetParent(A)`）|
|把物体从父下摘出来|`SetParent(null)`|
|换父但物体在世界里别动|`SetParent(newParent)`（默认 true）|
|换父且保持相对新父的偏移数值|`SetParent(newParent, false)`|
|子物体归到父身上|`localPosition = Vector3.zero`|
|物体归到世界原点|`position = Vector3.zero`|

##### 0. 一句话速记

协程**不是自己会走**，是 **Unity 引擎每帧在帧循环的固定钩子上调 `MoveNext()` 驱动它走一步**。协程的**命绑在 MonoBehaviour 的"存在/激活"上**（不是脚本 enabled）：Destroy / SetActive(false) → 停；脚本 `enabled=false` → **照跑**。

---

##### 1. 核心：谁每帧驱动协程

- C# 里 `IEnumerator` 是"能暂停/恢复的迭代器"，**自己不动**，得有人不停调 `MoveNext()` 才往下走。
- **Unity 里，这个人是引擎**：`StartCoroutine(xxx())` → Unity 把协程登记到场景的协程调度器 → **主循环每帧在生命周期的特定位置调一次 `MoveNext()`**，让它从上次 `yield` 走到下一个 `yield`。
- `yield return null` = "这步到此，把控制权交回 Unity，下一帧再调我" → 那个"下一帧"就是主循环的下一次迭代。

> 所以协程能"跨帧"却仍在主线程：它没有并行，只是被帧循环**切成一帧一步**喂着走。

---

##### 2. 不同 yield 挂在帧循环的哪个钩子（恢复时机）

|yield 写法|何时恢复|
|---|---|
|`yield return null`|下一帧的 Update 之后|
|`yield return new WaitForSeconds(t)`|等够 t 秒（游戏时间），Update 之后那个时机|
|`yield return new WaitForFixedUpdate()`|FixedUpdate 之后|
|`yield return new WaitForEndOfFrame()`|这一帧渲染全画完之后（常用于截屏）|

> 核心：协程每一步恢复都挂在帧循环某个**固定钩子**上，由引擎每帧驱动。不同 yield = 挂不同钩子。

---

##### 3. 核心：协程的命绑在谁身上（destroy / disable / SetActive）★高频坑★

`StartCoroutine` 是 **MonoBehaviour** 的方法 → 协程的命绑在"启动它的那个 MonoBehaviour"身上。三种情况分清：

|操作|协程会怎样|
|---|---|
|`Destroy(gameObject)` / Destroy 该组件|**停**（静默，不报错、不抛异常，后面代码永不执行）|
|脚本 `enabled = false`|**照跑**（反直觉！disable 脚本**不停**协程）|
|`gameObject.SetActive(false)`|**停**（且 SetActive(true) **不自动重启**，要重新 StartCoroutine）|

**核心逻辑**：协程绑的是 MonoBehaviour 的 **"存在/激活"**（物体在不在），**不是它的 `enabled`**。

- 物体在不在（Destroy / SetActive）→ 决定协程生死。
- 脚本 `enabled` → 只管"跑不跑 Update 那些回调"，**管不着已启动的协程**。

**想停协程**：显式 `StopCoroutine` / `StopAllCoroutines`，或 Destroy / SetActive(false)。别指望 disable 脚本能停。

---

##### 4. 两个时间/嵌套细节

###### `WaitForSeconds` vs `WaitForSecondsRealtime`（受不受 timeScale 影响）

- `WaitForSeconds(1f)`：等**游戏时间**，受 `Time.timeScale` 影响。`timeScale = 0`（暂停）时 → **永远等不完**（游戏时间冻结）。
- `WaitForSecondsRealtime(1f)`：等**真实时间**（墙上时钟），**不受 timeScale 影响**，暂停时照样倒计时。

**判据**：跟游戏逻辑走的用 `WaitForSeconds`；**暂停时也要走的**（暂停菜单 UI 动画、真实倒计时）用 `WaitForSecondsRealtime`。

> 典型坑：暂停菜单（timeScale=0）里协程想"1 秒后弹提示"，用 `WaitForSeconds` 永远弹不出来。

###### `yield return StartCoroutine(...)`（嵌套等待）

```csharp
yield return StartCoroutine(另一个协程());
```

= 启动"另一个协程"并**卡在这里等它整个跑完**，它结束当前协程才继续。用途：把一串异步步骤**串成顺序**（放动画→等完→加载→等完→开始）。

> 现代等价：`yield return 另一个协程();`（直接 yield 那个 IEnumerator）。

---

##### 5. 应用速查

|需求|怎么写|
|---|---|
|下一帧再继续|`yield return null`|
|等 t 秒（随游戏暂停停）|`yield return new WaitForSeconds(t)`|
|等 t 秒（暂停也要走）|`yield return new WaitForSecondsRealtime(t)`|
|等物理帧后|`yield return new WaitForFixedUpdate()`|
|等渲染完（截屏）|`yield return new WaitForEndOfFrame()`|
|等另一个协程跑完再继续|`yield return StartCoroutine(其他协程())`|
|停止协程|`StopCoroutine(...)` / `StopAllCoroutines()`（disable 脚本没用）|

##### 6. 踩过的错（错 → 正）

- 错（C# 那轮）：协程会内存泄漏 **正：协程停掉是"静默停止"，Destroy 物体后协程就地消失、不报错，不是泄漏。**
- 易错反直觉点：以为"disable 脚本 = 协程停" **正：脚本 `enabled=false` 协程照跑；协程绑的是物体存在/激活，不是脚本 enabled。**

> 归类：destroy/disable/SetActive 对协程的不同影响，属 **"绑定关系搞清楚"**（协程绑 MonoBehaviour 的存在，不绑 enabled）；WaitForSeconds 暂停等不完属 **deltaTime 那类"游戏时间 vs 真实时间"** 的延伸。

##### 0. 一句话速记

**三模式差在"UI 画在哪个空间"**：

- **Overlay** = 3D 全渲完后，UI 单独糊在屏幕这块 2D 画布上（不进 3D 渲染、不比 z）。
- **Camera** = UI 被塞进 3D 场景、交给指定摄像机渲染、和场景物体一起比 z。
- **World Space** = UI 本身就是 3D 世界里的一个物体，有世界坐标、旋转、远近透视。

---

##### 1. 核心表

|Screen Space - Overlay|Screen Space - Camera|World Space|
|---|---|---|---|
|**UI 画在哪**|屏幕 2D 画布，3D 全部渲完后糊上去|3D 场景里、离摄像机一段距离的平面|3D 世界里任意位置的一个物体|
|**要不要挂摄像机**|不要|要（Render Camera 字段）|不直接依赖（就是世界物体）|
|**会被 3D 物体挡吗**|不会，永远最前|会，按 z 和场景物体排前后|会，就是个世界物体|
|**有远近透视吗**|无|无（UI 平面正对摄像机）|有，走近变大走远变小|
|**最典型用途**|绝大多数常规 HUD / 菜单|UI 里要显示 3D 模型|血条 / 伤害数字 / 世界提示牌|

---

##### 2. 原理 / 机制（从"UI 被画在哪个空间"推）

**Overlay**：UI 不参与 3D 场景那套渲染。等所有 3D 物体都渲染完了，UI 作为**最后一道**，直接糊在屏幕这块 2D 画布上。所以它永远盖在最前、和 3D 物体谈不上比深度——因为它压根不在同一个渲染环节里。最省事，也是为什么常规 HUD 都用它。

**Camera**：把 Canvas 交给 Render Camera 字段关联的那台摄像机后，这块 Canvas 就被**摆进了 3D 空间**（离摄像机一段距离的一个平面）。它这时候就是个**和 Cube 平起平坐的 3D 对象**——一起进摄像机那套渲染、一起按 z 排前后。所以摄像机看到什么样、就渲成什么样；UI 被 z 更小的物体挡住，渲出来就是被挡住的。

> **关键**：不是"摄像机顺便把 UI 渲了"，是**UI 本身变成了 3D 场景里的一员**，才会跟场景物体比 z。这一点和 World Space 是连着的——都是"UI 进了 3D 空间"。

**World Space**：更彻底——这块 Canvas 就是个放进 3D 世界的**普通物体**，有自己的世界坐标、会旋转、有远近透视。跟场景里一堵墙、一个牌子没区别。你走近它变大、走远变小。

**三者递进关系**：Overlay（完全不进 3D）→ Camera（进 3D、但是贴着摄像机的一块平面）→ World Space（进 3D、且是世界里任意位置的自由物体）。

---

##### 3. 精髓 / 边界

**Camera 模式解锁的独有能力：UI 和 3D 物体在 z 上交错叠放。** 既然 Camera 模式下 UI 进了 3D 渲染管线、和场景物体同池排序——就能做到：粒子特效穿插在 UI 之间、3D 物体一部分露在 UI 前面一部分在后面。Overlay 因为是"最后一道、整块糊上去"，UI 要么全在前、要么谈不上和场景比深度，做不了这种交错。

**面试易答窄的点**：World Space 不要说成"VR/AR 专用"。正确框法——"凡是 UI 要待在 3D 世界里、有空间位置和远近，而不是贴在屏幕上，就用它"。

---

##### 5. 关键细节 / 陷阱

- **Camera 模式：z 的比较对象是场景物体，不是别的 UI。** UI 被挡是因为它成了 3D 对象、和 Cube 比 z。别和"UI 之间谁盖谁"（那由层级顺序 / Sorting 决定）混。
- **World Space 最常见的不是科幻投影，是血条。** 敌人头顶血条 / 名字（跟着怪在世界里跑、绕到侧面还在头上、离远变小）、飘的伤害数字、NPC 头顶感叹号、可交互物旁的"按 F 拾取"——这些日常需求全是 World Space UI。别被"3D 投影面板"那种炫的例子带偏，以为它很特殊。

---

##### 6. 应用速查

|需求|用哪个模式|为什么|
|---|---|---|
|常规血条条（屏幕角落）、菜单、设置界面|Overlay|最省事，永远最前，不需要和 3D 交互|
|背包里旋转查看装备的 3D 模型、UI 里嵌 3D 预览|Camera|UI 要和 3D 模型一起渲、一起比深度|
|粒子 / 3D 物体要和 UI 在深度上交错|Camera|要 UI 参与 3D 渲染管线的排序|
|敌人头顶血条 / 名字、场景里飘的伤害数字|World Space|UI 要跟在世界物体上、有远近|
|NPC 任务感叹号、"按 F 拾取"提示|World Space|挂在世界物体上的空间提示|
|立在空间中的操作面板（科幻风）|World Space|世界里的自由 UI 物体|

---

##### 7. 踩过的错（错 → 正）

- **错**：World Space Canvas 是 VR/AR 专用 → **正**：凡 UI 要待在 3D 世界里、有空间位置和远近就用它（血条 / 伤害数字 / 提示牌都是），VR 只是其一。

---

##### 0. 一句话速记

**事件中心 = 广播/订阅的"中间人"。** 发出者只喊"发生了 X"、不认识谁在听；响应者各自订阅 X、自己写逻辑。 **解耦的本质** = 发出者和响应者**彼此没有直接引用**，都只依赖中间人（事件中心）。

---

##### 1. 核心表

|不用事件中心（直接调用）|用事件中心（广播/订阅）|
|---|---|---|
|玩家死亡代码|直接调 uiManager/audioManager/… 每一个|只 `广播("玩家死亡")` 一句|
|玩家死亡认识谁|**认识所有响应者**（持引用、知方法名）|只认识事件中心，不知道谁在听|
|加"通知排行榜"|**改玩家死亡代码**，加一行调用|排行榜**自己订阅**，玩家死亡代码不动|
|耦合程度|高（牵一发动全身）|低（发出/响应互不引用）|

---

##### 2. 原理 / 机制

**① 不用事件中心的痛点（把耦合看清）**

```
// 玩家死亡时
uiManager.显示结算界面();
audioManager.播放失败音乐();
saveSystem.记录存档();
achievementSystem.判断成就();
```

玩家死亡代码**必须认识上面每个 Manager**（持引用、知方法名）。后果：

- 加"通知排行榜" → 回来改这段、加一行。
- 某 Manager 方法改名/删除 → 这段也得改。
- 玩家死亡逻辑和这四五个系统**焊死**——就是"牵一发动全身"。

**② 事件中心怎么拆开它**

玩家死亡时只干一件事：

```
eventCenter.广播("玩家死亡");   // 不知道也不关心谁会响应
```

各 Manager **自己去订阅**：

```
eventCenter.订阅("玩家死亡", 显示结算界面);   // UIManager
eventCenter.订阅("玩家死亡", 播放失败音乐);   // AudioManager
// 存档、成就…各自订阅
```

事件中心收到"玩家死亡"广播后，**自动通知所有订阅者**，挨个调用它们注册的方法。

**③ 加需求为什么不动原代码（解耦的落点）** 加"通知排行榜" → 只需排行榜**自己订阅"玩家死亡"**、写自己的逻辑。**玩家死亡那段代码一个字都不用动。** 因为发出者只依赖中间人、不认识任何具体响应者。

**④ 事件中心内部是什么** 本质是一个容器（通常是字典：key=事件名，value=订阅了这个事件的方法列表）。

- 订阅 = 往对应事件的方法列表里加一个方法引用。
- 广播 = 找到该事件的方法列表、挨个调用。
- 取消订阅 = 从列表里移除那个方法引用。

---

##### 3. 精髓 / 边界

**"发出者不认识接收者"是解耦的核心判据。** 判断一个设计有没有真解耦，就看：发出方是否需要持有接收方的引用、知道接收方是谁。事件中心让两边都只依赖中间人 → 彼此可独立增删改，互不影响。

---

##### 5. 关键细节 / 陷阱

**订阅了就必须取消订阅（反订阅）——否则报错或内存泄漏。**

- 事件中心内部拿容器存着"谁订阅了"（方法引用）。
- 一个对象订阅了、后来被销毁却**没取消订阅** → 事件中心里还留着它的引用。下次广播时去调**已销毁对象**的方法 → 报错；或对象因被事件中心引用着、**GC 回收不掉 → 内存泄漏**。
- 这就是委托事件那里讲的"**订阅列表持有引用 → GC 判定有引用 → 回收不掉**"——同一个机制，只不过订阅列表住在事件中心里。
- **铁律（和委托事件、Unity 生命周期一致）**：订阅（OnEnable）和取消订阅（OnDisable/OnDestroy）**成对出现**。

> **同源提醒**：委托事件订阅/反订阅、事件中心订阅/反订阅、生命周期 OnEnable/OnDisable、对象池取/还——都是"**成对操作**"的同一个直觉。撞到"注册/订阅/取出"，就想它的反面"注销/退订/归还"。

---

##### 6. 应用速查

|场景|用事件中心怎么做|
|---|---|
|一个事件要通知多个互不相关的系统|发出方广播、各系统自己订阅|
|两个模块要通信但不想互相引用|通过事件中心中转，双方只依赖中心|
|频繁增删响应者（加新系统）|新系统自己订阅，不动发出方|
|对象销毁前|务必取消订阅（成对）|

##### 0. 一句话速记

**对象池 = 用"藏/显（SetActive）+ 归还/取出"替换"销毁/创建"。** 省两笔：**创建端**（分配内存 + 实例化整棵组件树）、**销毁端**（产生垃圾触发 GC 卡帧）。 只对"**高频、反复、同类**"的对象划算。

---

##### 1. 核心表

|直接 Instantiate/Destroy|对象池|
|---|---|---|
|要用时|Instantiate 造新的|从池取一个（藏着的激活拿来用）|
|用完时|Destroy 销毁|SetActive(false) 藏起来、还回池|
|创建端开销|分配内存 + 实例化组件树|池里有货时=0（对象早造好）|
|销毁端开销|产生垃圾 → GC 卡帧|不产生垃圾（没销毁）|
|代价|无（但高频时很贵）|常驻内存 + 管理复杂度|

---

##### 2. 原理 / 机制

**① 为什么 Instantiate/Destroy 贵（对称的两头）**

- **Instantiate 贵在**：①分配内存（也在给 GC 攒未来的活）②实例化整棵组件树——Prefab 带一堆组件（Transform/渲染器/脚本/子物体），要全造出来、初始化每个、跑 Awake/OnEnable。对象越复杂越重。
- **Destroy 贵在**：销毁的对象变成**垃圾**，**GC 迟早来处理**，而 **GC 回收会卡帧**。频繁 Destroy → 频繁产生垃圾 → GC 频繁触发 → 卡顿。
    
    > 这个 GC 就是装箱拆箱、协程内存泄漏那里的同一个 GC。
    

**② 池子怎么省掉这两笔**

- **不销毁**：用完 SetActive(false) 藏起来、塞回池子。没变垃圾 → GC 没活 → 不卡。
- **不创建**：要用时从池里取一个藏着的、SetActive(true)。对象早造好（组件树现成）→ 省分配 + 实例化。
- 池空了才真 Instantiate 造新；平时在"藏/显"之间循环。

**③ "取对象"的完整步骤流（本轮漏步重点）**

1. 检查容器里有没有空闲对象。
2. **有** → 取出来 + **从容器移除**（否则重复分配同一对象）+ **SetActive(true) 激活**（否则取出来是隐形的）。
3. **没有** → Instantiate 造新的 + 同样激活。
4. 返回这个对象。

**④ "还对象"的步骤流**

1. SetActive(false) 藏起来。
2. （可选）重置状态、把它塞回容器。

> 取（显）/ 还（藏）成对。

**⑤ 池子的可配置性（造什么、造多少，由调用方决定）** 对象池是给别的脚本用的，池里对象不一定是子弹——要**通用**。所以：

- **造什么（Prefab）**：调用方创建池时把 Prefab 传进来，池拿它去 Instantiate。
- **造多少（预热数量）**：调用方说了算。
- **常见结构（通用池 / PoolManager）**：一个总管理器管多种对象，内部"**每种 Prefab 对应一个容器**"（字典：key=Prefab/名字，value=该种对象的容器）。调用方说"给我一个这种"，管理器找对应容器取。

**⑥ 依赖关系（前提 vs 优化，别捆一起）**

- **容器创建（new List/Queue）= 最低前提**：没容器，取/还操作谁？
- **预热（开局先造一批）= 可选优化**：不预热池子开局是空的，第一次取走"没有就 Instantiate"分支兜底、也能跑，只是开局没享受到复用。
- 精确依赖链：容器创建 → 取/还可工作 → 预热是锦上添花。**别把"容器创建"和"预热"焊成一个必须步骤**——对象池不预热也能工作。

---

##### 3. 精髓 / 边界（何时不该用）

**对象池自己有成本**：①池里藏着的对象 SetActive(false) 仍**占内存**（拿内存换性能）②管理复杂度（取还逻辑 + 状态重置）。

**什么时候不值得 / 负优化**：

- **低频生灭**：一局只造一两次的东西（Boss、固定的门）——没"频繁"开销可省，却要一直占池子内存。省的 < 常驻内存代价 → 负优化。
- **种类极多、每种只用一两个**：池要为每种留常驻实例，内存全砸在"备着但很少用"上。
- 一句话：**只对"高频、反复、同类"划算**（子弹/特效/怪/伤害数字）；低频或杂而少的用池子是拿内存换了个用不上的性能。

---

##### 5. 关键细节 / 陷阱

- **取出复用前必须重置状态**：对象是"上次用完藏起来的"，身上可能留着上次残留——血量没满、位置没归零、挂着上次的特效、协程还在跑。直接用 = 带脏状态。取出时重置（血满、位置摆好、清残留）。
    
    > 同源：单例 DontDestroyOnLoad 状态残留、事件中心反订阅——**复用/长命的东西必须管好状态清理与重置**，否则上次残留污染下次。
    
- **取/还 = SetActive(true)/SetActive(false) 成对**——又一个成对操作（委托订阅/退订、事件中心订阅/反订阅、生命周期 OnEnable/OnDisable 同型）。

---

##### 6. 应用速查

|需求 / 现象|做法 / 原因|
|---|---|
|子弹/特效/怪/伤害数字（高频生灭）|用对象池，取时激活、还时藏起来|
|Boss/固定门（低频）|别用池，直接 Instantiate/Destroy|
|取出的对象带着上次的脏状态|取出时重置状态|
|取出的对象看不见|检查取出时是否 SetActive(true)|
|同一对象被多处用、画面乱|检查取出时是否从容器移除|
|一个池管多种对象|PoolManager + 字典（每种 Prefab 一个容器）|

---

#### 2. 原理 / 机制（带锚点，非光秃结论）

**① 反射防构造（为什么绕这一圈）**：
`new()` 约束要求 T 有**公共**无参构造 → 公共=外部谁都能 `new SomeMgr()` → 破坏唯一性。堵法：构造改**私有** → 但私有了 `new()` 挂不上、`new T()` 编译不过 → 只能用**反射**绕过访问权限调私有构造。
> 因果链：私有构造堵外部 → 堵死了自己 → 反射开后门。

**② 双检锁（为什么判两次空）**：
```csharp
if (instance == null)        // 外层：性能门。已创建则后续调用直接返回，不进锁
{
    lock (lockObj)
    {
        if (instance == null) // 内层：正确性门。防两个线程都过了外层、排队进锁后重复创建
        { /* 创建 */ }
    }
}
```
- 外层没了 → 每次调用都抢锁（白白慢）。
- 内层没了 → 并发时A建完B进锁不复查、又建一个（唯一性破）。
- 名字由来：判两次，一次为快、一次为对。

**③ 饿汉“天生线程安全”的根**：
饿汉 `private static T instance = new T();` 把创建挂在**类加载**时机 → 类加载由 **CLR** 管、CLR 保证一个类**只加载一次且线程安全** → 饿汉**白嫖**了这个安全，不用自己写锁。
对比懒汉：创建在“运行时第一次访问”、由**你的代码**控制，多线程能同时闯进getter → 得自己加锁。

**④ abstract 的分工（堵哪个口子）**：

| 机制 | 堵的口子 |
|---|---|
| `abstract` | 外部 `new BaseManager<XXX>()`（实例化基类本身） |
| 子类私有构造+基类反射 | 外部 `new SomeMgr()`（实例化子类） |
两者各管一个入口，合起来封死“从任何入口new出实例”。

---

#### 3. 精髓 / 边界

- **static 保证的是“归属+份数”，不是“唯一性结果”**：static = 字段属于**类**、全局**只有一份**（所有对象共享同一个）。“唯一性”是这个的**结果**，“类名直接点/不用实例化就能访问”是同一本质的另一侧面。别答成“哪都能调”（那是public）、也别直接跳到“唯一性”。
- **getter 创不创建 = 三变种的分水岭**：自动挂载式getter负责创建（发现null自己造）；挂载式getter**只返回不创建**（实例只能靠人拖，getter无权造，造了就变成自动挂载式了）。
- **abstract 两版必要性不同**：不继承版基类能new、**必需**abstract；自动挂载版继承Mono不能new+泛型不能挂、**两条创建入口天生封死**，abstract可选（加了只为表意统一）。

---

#### 4. 选型映射（看到什么 → 用哪个）

| 需求特征 | 选择 |
|---|---|
| 不进场景、纯逻辑/数据 + 想省心 | `Lazy<T>` |
| 不进场景 + 想手写理解线程安全原理 | 双检锁（面试讲原理经典写法） |
| 要生命周期(Update/协程/场景切换) + 纯代码配置 | 自动挂载式 |
| 要生命周期 + 要Inspector拖资源/配参数 | 挂载式 |
| 组件“编译时就确定要、且要能配置” | 编辑器手动挂 + `GetComponent` |
| 组件“运行时才动态决定要不要/要几个” | `AddComponent` |

**判据内核**（贯穿单例选型和Get/Add）：**能在编辑器里配的，就别用代码写死。**

---

#### 5. 关键细节 / 陷阱

- **`static` 别漏**：单例的 instance 字段和 Instance 属性**都必须static**。漏了→每个对象各存一份、判重拿自己比自己、唯一性失效。
- **Destroy / DontDestroyOnLoad 传物体不传组件**：`Destroy(gameObject)`、`DontDestroyOnLoad(gameObject)`。传 `this`（组件）→ Destroy只删脚本留垃圾物体；DontDestroyOnLoad传组件不对（要传GameObject）。
- **挂载式 Awake 判重必须在登记前**：先 `if(instance!=null){Destroy(gameObject);return;}` 再 `instance=this as T`。反了→先登记后判重、拿自己比自己恒成立、把自己删掉。
- **挂载式 null = 没人挂脚本**（异常路径）：getter返回null不是“该造还没造”，是“忘了往场景拖脚本”。这是挂载式固有弱点（把“实例存不存在”赌在人记不记得挂上）。自动挂载式无此问题。
- **泛型 MonoBehaviour 不能直接挂**：`SingletonAutoMono<T>` 本身不能拖/AddComponent，必须先写具体子类 `class XxxMgr : SingletonAutoMono<XxxMgr>`，挂子类。
- **自动挂载式撞车（手动+自动）**：若有人手动拖了一个、getter又发现null自动造一个 → 两个实例。想防就得加Awake判重，但那就失去自动挂载式的简洁——是取舍非改进。
- **AudioSource 拿哪个**：同物体挂两个同类组件时 `GetComponent<AudioSource>()` 分不清 → 做成两个可拖字段（Inspector拖对）。验证是否同一个用 `GetInstanceID()` 比对。

#### 7. 踩过的错（错 → 正）

- static 保证“哪都能调” / “唯一性” → 正：static 保证**属于类、全局只有一份**（归属+份数）；“哪都能调”是public、“唯一性”是结果。
- `Destroy(this)` / `DontDestroyOnLoad(this)` → 正：传 `gameObject`（物体），不是 `this`（组件）。
- 挂载式基类 `instance` 忘加 static → 正：必须 static，否则每对象一份、判重失效。
- 迁移作业选型说“挂载式”、代码却继承 `SingletonAutoMono` → 正：选型和继承必须一致，要Inspector配就继承 `SingletonMono`。
- audioSource 用 `AddComponent` 拿 → 正：挂载式场景该 `GetComponent`（让source在Inspector可配）；AddComponent仅用于运行时动态加。
- 挂载式 getter null “不可能发生” → 正：没人挂脚本时Awake不执行、instance为null、调用空引用。挂载式固有弱点。

#### 8. 新用法/新类/新关键字（本轮新接触 · 实用）

**`readonly`（关键字）** —— 只读字段修饰符。
`private static readonly object lockObj = new object();`
用途：字段只能在声明时或构造函数里赋值，之后不能再重新赋值。用来锁死"这个字段的指向不许被换掉"——单例里 lockObj / Lazy 字段都用它，防运行中被掉包导致锁失效或实例被重造、唯一性破。
⚠ 边界：锁的是"字段指向"（不能改指向别的对象），不是锁对象内部状态；对引用类型，对象内部照样能变。

**`Lazy<T>`** —— 线程安全的延迟初始化泛型类。
`private static readonly Lazy<T> lazy = new Lazy<T>(() => new T()); // 访问 lazy.Value 时才创建`
用途：一个类型包掉双检锁那套（懒加载 + 线程安全），替代手写双检锁。
⚠ 边界：靠 `new T()` 创建，**只能用于不继承Mono的单例**（继承Mono不能new）。

**`[RequireComponent(typeof(AudioSource))]`** —— 加在类上的特性。
`[RequireComponent(typeof(AudioSource))] public class AudioManager : SingletonMono<AudioManager> { }`
用途：挂这个脚本时Unity自动把依赖的组件也挂上、且不允许删，从源头保证依赖组件存在、且在Inspector可配。
⚠ 边界：**只保证挂一个**。需要同类型多个组件（如BGM+音效两个AudioSource）时不适用。

**`GetInstanceID()`** —— 每个对象实例的唯一ID。
`Debug.Log(bgmSource.GetInstanceID() == sfxSource.GetInstanceID()); // 判两个引用是不是同一个对象`
用途：验证“两个变量到底指不指向同一个对象”的通用手段。同物体多个同类组件、下拉框看不出区别时用它自证。
⚠ 边界：调试/验证用，不写进正式逻辑。

**`AudioSource.PlayOneShot(clip)`** —— 叠加播放一次性音效。
`sfxSource.PlayOneShot(clip); // 不占用clip字段、多个音效可同时响、互不打断`
用途：播音效的标准做法，替代 `clip=x; Play()`（后者会互相打断、且占用clip字段）。
⚠ 边界：适合一次性音效；循环的BGM还是用 `clip + loop + Play()`。

##### 不继承Mono 双锁 单例模式基类

```csharp
public abstract class SingletonBase<T> where T : class
{
    private static T instance;
    protected static readonly object lockObj = new object(); 
    public static T Instance 
    {
        get 
        {
            if (instance == null) //外层锁 是否抢锁
            {
                lock (lockObj) 
                {
                    if (instance == null) //内层锁 判空
                    {
	                    //反射调无参构造
                        Type type = typeof(T);
                        ConstructorInfo constructor = type.GetConstructor
                        (
                            BindingFlags.Instance | BindingFlags.NonPublic, //表示成员私有方法
                            null, //表示没有绑定对象
                            Type.EmptyTypes, //表示没有参数
                            null //表示没有参数修饰符
                        );
                        if (constructor != null)
                            instance = constructor.Invoke(null) as T;
                        else
                            Debug.LogError("没有找到私有无参构造函数");
                    }
                }
            }
            return instance;
        }
    }
}
```

public class SingletonMonoBase<T> : MonoBehaviour where T : MonoBehaviour

    public static T Instance => instance;
    protected virtual void Awake()

        }

    }

            {

        }

#### 0. 一句话速记

**MonoMgr = 住在场景里的替身:用自己真实的生命周期和协程能力,替所有不继承Mono的脚本打工。** 一个真Update驱动N个假Update(event存方法 → 真Update里Invoke)。

---

#### 1. 核心表

|基类|本质|何时用|例子|
|---|---|---|---|
|不继承Mono(BaseManager)|纯逻辑单例,不依附场景|纯逻辑、跨场景、不用配|BuffManager / EventManager / SaveManager|
|自动挂载式|依附场景,自己 new+AddComponent 不用手挂|要生命周期/协程,纯代码驱动不用配|**MonoMgr本身**、全局计时器|
|挂载式|依附场景,必须手动挂|要生命周期,且要在Inspector配引用/参数|AudioManager(配AudioClip)、GameManager|

MonoMgr 继承**自动挂载式**:它是管理器(纯逻辑单例)→要单例;又必须有真生命周期回调才能替人打工→要Mono功能;但纯代码驱动、不用配→自动挂载式(非挂载式)。

---

#### 2. 原理/机制

**核心链(帧更新)**

1. MonoMgr 内部存 event(UnityAction),存一堆"假Update"方法
2. 外部脚本调 AddUpdateListener,把自己的方法 += 进 event
3. MonoMgr 自己的**真 Update()**(Unity每帧自动调)里 event?.Invoke()
4. → 一个真Update,把所有订阅进来的假Update全带跑

**协程借力**:不继承Mono的脚本没有 StartCoroutine 能力(那是MonoBehaviour的)。MonoMgr有 → 提供 StartCor(IEnumerator) 转调自身 StartCoroutine,让别人借它的手开协程。

---

#### 3. 精髓/边界

- **"存"和"调"是两件事**:订阅方法只负责把方法**存**进event;真生命周期函数才负责每帧**调**。少了后者,方法塞进去是死的、没人跑。
- **event必须private**:已提供Add/Remove作唯一入口,event就该藏死。public=留两个入口,自相矛盾,内部实现改不动。

---

#### 4. 选型映射

拿到需求 → 选哪种基类,判据链:

1. **要不要在编辑器配引用/参数?** 要 → **挂载式**(锁死,别的不用看)
2. 不用配 → **要不要生命周期/协程?** 要 → **自动挂载式**
3. 都不要(纯逻辑) → **不继承Mono**

**最强分水岭 = "要不要配东西"**:一旦要配引用 → 直接锁挂载式。

---

#### 5. 关键细节/陷阱

- **同名方法撞父类**:StartCoroutine/StopCoroutine 若在MonoMgr里同名,方法体调自己 → 无限递归 → StackOverflow。借用就改名(StartCor),故意覆盖才加 new。
- **?.Invoke() 判空**:event 没订阅者时是 null,裸调 .Invoke() → NRE。必须 ?.Invoke()。
- **停协程要停"当初那一个"**:StopCor(重新调协程方法()) 传的是全新迭代器,MonoMgr没在跑它,停不掉。必须存住开时的 Coroutine 句柄,停那个。
- **停完置空句柄**:cor 停完置 null,让 if(cor!=null) 判断诚实(不置空下次误判"还在跑")。
- **谁注册谁注销**:Mono脚本在 OnDisable/OnDestroy 里 -=;非Mono脚本(BaseManager)没自动回调 → 自己造成对 Open/Close 方法,外部在合适时机(如玩家死亡)手动调 Close 注销。

---

#### 6. 应用速查

|任务|怎么写|
|---|---|
|让非Mono脚本每帧执行|MonoMgr.Instance.AddUpdateListener(自己的方法)|
|停止每帧执行|RemoveUpdateListener(同一个方法)|
|非Mono脚本开协程|cor = MonoMgr.Instance.StartCor(协程方法())|
|停指定协程|if(cor!=null){ StopCor(cor); cor=null; }|
|停所有协程|MonoMgr.Instance.StopAllCor()|

**非Mono管理器用MonoMgr的标准姿势(成对Open/Close)**:

```csharp
public class BuffManager : SingletonBase<BuffManager>
{
    private BuffManager() { }

    public void OpenBuffCheck()
    {
        MonoMgr.Instance.AddUpdateListener(BuffCheck);
    }

    public void CloseBuffCheck()
    {
        MonoMgr.Instance.RemoveUpdateListener(BuffCheck);
    }

    private void BuffCheck()
    {
        // 每帧检查逻辑
    }
}
```

#### 7. 踩过的错(错 → 正)

- 协程开关方法与父类同名 StartCoroutine、体内调自己 → 正:无限递归会 **StackOverflow**;借用改名 StartCor,或 base./new
- 无限递归后果答"内存泄漏" → 正:是**栈溢出 StackOverflowException**,不是内存泄漏
- CloseBuffCheck 里写成 AddUpdateListener → 正:关闭要 Remove,有增就有减
- 停协程传 StopCor(协程方法()) → 正:那是新迭代器,要存住开时的 Coroutine 句柄、停那个
- 停协程后不置空 cor → 正:置 null 让判断诚实(否则误判还在跑)
- ?.Invoke() 说不清何时 null → 正:event 无订阅者时为 null
- 字典版:Add 用 ContainsKey 防、Update 直接取 key(混用)→ 正:统一策略,Awake 一次预填全部 key
- 字典声明后没 new → 正:Awake 里 new
- ClearAllEvent 一把清空 → 正:会误伤跨场景长命对象、违反谁注册谁注销,删掉

#### ★ 8. 新用法/新类/新关键字

- **GetInvocationList()**:`foreach (var d in evt.GetInvocationList()) (d as UnityAction)?.Invoke();` — 返回委托里所有订阅方法的数组(Delegate[]),用来逐个单独调用。⚠每帧调有生成数组开销。
- **Coroutine(句柄)**:`Coroutine cor = StartCoroutine(...);` — StartCoroutine 的返回值,存住它才能精确 StopCoroutine(cor)。⚠停完置 null。
- **StopCoroutine 重载**:既能收 IEnumerator 也能收 Coroutine 句柄。用句柄停最稳。
- **StopAllCoroutines()**:一把停掉该 MonoBehaviour 上所有协程。
- **base.**:`base.StartCoroutine(r)` — 子类调被自己同名方法遮住的父类方法(单例轮 base.Awake 同款)。
- **enum + Dictionary 合并同类项**:`Dictionary<E_UpdateType, UnityAction>` 把三套 event 合一套。⚠代价:字典要 new、key 要预填、维护负担↑。

		FixedUpdate = 2,

	{

#### 0. 一句话速记

**对象池 = 柜子(Dictionary 按名字分类)+ 抽屉(闲置容器)+ 取/放/清;两套并行——GameObject 池(会悬空,靠 SetActive/父子管理)和纯C#对象池(靠引用存活、永不悬空,只排队进出)。** 上限约束加"入口"(要不要造新的),不加"出口"(有闲置永远优先复用)。

#### 2. 原理/机制(带锚点)

**为什么池化省性能——两条独立的 GC 链**(⚠ 面试高频,精确讲):

- **Instantiate**:堆分配(CPU+堆增长)→ **堆增长到阈值就触发 GC**(不需 Destroy 参与)+ 深拷贝(递归复制整棵组件树)。
- **Destroy**:制造垃圾 → **加重 GC 单次清理量**。
- ⚠ 两个**独立**喂 GC,非串联:一个管"GC多久来一次"(堆增长),一个管"GC来一次清多少"(垃圾)。**只 Instantiate 不 Destroy 照样触发 GC。**

**GC 为什么卡帧**:GC 触发时 **Stop-The-World**——暂停游戏线程、冻结引用图、做可达性分析(标记-清除),这一冻就掉帧。

**深拷贝**:Instantiate 给每个实例独立的整棵树(GameObject+所有组件+子物体递归复制),对立面是浅拷贝(共享内部对象)。⚠ Mesh/Material/Texture 等**资源不深拷贝**,实例只引用同一份共享资源。

**抢占复用(上限层)**:栈空(说明已到上限)时,取 `usedList[0]`(最老)→ `RemoveAt(0)` → `Add` 到末尾。⚠ 抢的是**激活中**的对象,不需 `SetActive(true)`(它没灭过),也不失活、不进闲置栈——从一个使用者直接拽给另一个。

**里氏替换 + 向下转型(非Mono层)**:`PoolObject<Message>` 和 `PoolObject<Node>` 是不同类型、塞不进同一字典 → 都实现空接口 `IPoolObject` → `Dictionary<string,IPoolObject>`(父装子)→ 取出是 `IPoolObject`(父)→ `as PoolObject<T>` 转回子才能用队列。

---

#### 3. 精髓/边界 ※(最易漏的洞察)

**① `name` 一名多用**:同一字符串同时当【字典键】+【`Resources.Load` 路径】+【`obj.name` 校准】。任一处不一致(如 Instantiate 出的 `Cube(Clone)` 没改回 `Cube`),存取键对不上,池子永久命中失败、还堆死抽屉。

**② 上限约束加"入口"不加"出口"**:`maxNum` 限的是"要不要 **new 新对象**"(Instantiate 阈值),**不是**"同时在用数的物理上限"。`Pop` 有闲置永远优先复用(哪怕在用数已超 maxNum,因为复用不吃新内存)。预热必须受入口约束(count≤maxNum),否则绕过 Instantiate 破坏"总数≤maxNum"不变式,上限失效。

**③ 两类对象生命周期机制根本不同**:GameObject 能被 Unity 单方面 Destroy(切场景)→ 引用还在就悬空;纯C#对象只要被引用就绝不被回收 → **永不悬空**。这一条决定:两类池能否抢占(GameObject 有 SetActive 遥控器、纯C#没有)、切场景要不要清(GameObject 必清防悬空、纯C#不清也不崩只是内存)。

**④ 总数不变式(上限层)**:对象总数(Stack+Used)恒 ≤ maxNum。证明:总数只在 Instantiate 时+1,而 Instantiate 要求栈空(`Count==0`),栈空时总数=Used<maxNum → 锁死。**所以"栈空"在 Pop 内部 ⟺ "已到上限"**,Pop 判 `Count>0` 就够、不需 maxNum。

---

#### 4. 选型映射(需求特征 → 用哪个)

- 频繁 new/扔的**场景实体**(子弹/特效/飘字)→ GameObject 池。
- 频繁 new/扔的**纯内存对象**(消息/寻路节点/数据对象)→ 纯C#对象池。
- 低频 / 少而杂 / 唯一持久(Manager)→ **不用池**(收益<占用)。
- 需要"某类同时在场数量封顶"→ 上限层(v2 脚本配置优于 v1 传参)。
- 开发要看 Hierarchy 分类 → 开 `isOpenLayout`;**上线关**(SetParent 有开销)。
- 战斗前已知会大量用某对象 → 预热 Warm(count≤maxNum)。
- 容器选型:抽屉只两端进出 → Stack/Queue(**语义贴合**优先,性能无差);usedList 要删任意位置 → **List**(Queue 只能出队头,删中间别扭)。

#### 5. 关键细节/陷阱 ※

- **取对象两个收尾动作**:Instantiate 那条要 `obj.name = name`(去 Clone);Pop 出闲置要 `SetActive(true)`(池里是失活的)。**两个都易漏。**
- **PushObj 第一件事是 `SetActive(false)`**,且**提到分支外**(失活不依赖抽屉存在)。
- **建抽屉时机两类不同**:GameObject 池 GetObj 里 Instantiate 时建;**纯C#对象池 GetObj 取时不建、PushObj 才建**(取时没货直接 `new T()` 不登记)。
- **复合条件短路**:`!ContainsKey || (Count==0 && ...)`——`UsedCount<maxNum` 必须在**括号内**,否则没键时也访问 `dic[name]` → KeyNotFound。混用 `&&/||` 加括号明确分组。
- **柜子总根物体惰性判空创建**:`if(root==null && isOpenLayout) new GameObject("Pool")`,且**在用它之前**建(先建后用)。
- **传参别提前取成员**:构造函数收 `GameObject root` 不收 `root.transform`——开关关时 root 为 null,提前 `.transform` 会空引用;传整个对象、让接收方在保护逻辑里取。
- **ClearPool 两种场景**:切场景传 `destroyObj=false`(Unity 销毁,只清字典);手动清传 `true`(遍历 Destroy 实体防幽灵泄漏)。开关关时对象散落无父节点,要遍历各抽屉逐个 Destroy(销毁总根节点无效)。
- **`Destroy` 是延迟销毁**(本帧末),`Destroy(x)` 后可立即 `x=null`。
- ⚠ **判"抽屉有没有货"用 `Count>0`,不是 `!=null`**(Stack 对象存在≠里面有元素)。

- `!=null` 判抽屉有货 → **正**:`Count>0`(对象存在≠有元素)。
- 复合条件写成 `(A||B)&&C` → **正**:`A||(B&&C)`,UsedCount 判断进括号(否则没键时崩)。
- GC 由 Destroy 触发 → **正**:GC 由**堆增长**触发,只 Instantiate 不 Destroy 也触发;Destroy 只加重清理量。
- Instantiate 没接返回值、改了模板名 → **正**:`obj=Instantiate(Load(name))` 接住实例;Load 返回**共享模板不可改**。
- 纯C#对象池 PushObj 没抽屉时报错 → **正**:该**建抽屉**(纯C#池 Push 是唯一建抽屉时机)。
- 柜子总根先用后建 → **正**:创建挪到"用它"之前。
- Warning 先改 count 再打印 → **正**:先打印(用原值)再改。
- 抢占"尾移到头" → **正**:取 `[0]`(最老)→ 挪到末尾。
- 预热不限数 → **正**:count≤maxNum(否则破坏总数不变式)。
- class 约束"as 转型需要" → **正**:`as` 转的是 `PoolObject<T>`(本就引用类型),与 T 无关;class 约束作用是**限定只池化引用类型、挡值类型误用**。
- 把 GameObject 池特性套纯C#对象(上限/抢占/清空) → **正**:纯C#对象交出即失控、无遥控手段,做不了上限/抢占;永不悬空、不清也不崩。

#### ★ 8. 新用法/新类/新关键字(只记录,不进第9自测)

- **`where T : class, new()`**:`class PoolObject<T> where T:class,new()` — 泛型约束。`new()`=T须有公共无参构造(因 `new T()`);`class`=限引用类型(挡 struct 进池)。⚠ 缺 `new()` 编译不过;`class` 非必需但推荐。
- **`typeof(T).Name` / `.ToString()`**:`typeof(T).Name`→短名(`Message`);`.ToString()`→全名(带命名空间,不易撞名)。当泛型池的键。
- **`throw new System.Exception(...)`**:`if(poolObj==null) throw new System.Exception("...")` — 主动抛异常当场中断。⚠ 配置错误(忘挂脚本)该 throw(Fail Fast);运行时正常意外别 throw。
- **`as` 向下转型**:`objDic[key] as PoolObject<T>` — 父类型转子类型,失败返 null(硬转 `(T)` 失败抛异常)。⚠ 这里 as 的"安全"是假象(下一行 `.queue` 仍会空引用)。
- **表达式体属性**:`public int Count => _stack.Count;` — 只读属性简写,等价 `get{return...}`。配"最小暴露"用(暴露只读 Count,不暴露整个 Stack)。
- **`GetComponent<T>()`**:`usedObj.GetComponent<PoolObj>()` — 读挂在对象上的组件(v2 读上限脚本)。⚠ 建抽屉时读一次缓存,别每次读。

#### ⭐ 编码原则/设计经验(可迁移,只记录,不进第9自测)

> 归属:多为 Claude 供、用户判"值得沉淀";标 ★ 的是用户主导。

- **选容器先看语义贴合,再看性能**:性能相近时,接口能否直接表达意图是首要依据(Stack `Push/Pop` 一眼是"后进先出桶";List 要 `Add+RemoveAt(Count-1)` 绕)。代码写给人读。
- **封装/最小暴露**:私有字段 + 只读属性,暴露**结论**(`NeedCreate`/`Count`)不暴露**原料**(`maxNum`/内部容器)。给外部"够用的最小权限"。
- **Fail Fast > 静默兜底**:配置错误/编程错误当场报错或 throw,别给错误默认值悄悄跑(带病继续跑,错误推迟到很远才暴露,debug 成本剧增)。⚠ 区分"编程错误"(Fail Fast)vs"运行时正常意外"(优雅容错)。
- **幂等操作可无条件执行,非幂等必判断**:`SetActive(true)` 对已激活对象无副作用 → 可无条件写省 if;有副作用的操作(计数+1/发事件)必须判断。
- **单一数据源(SSoT)**:配置集中一处(v2 上限挂 Prefab 脚本),别散在各调用点(v1 每处 `GetObj("X",5)` 易不一致)。
- **★ 分支分析 = 逻辑覆盖 + 可达性**:取反(德摩根)只得"逻辑上覆盖哪些组合",其中有的是**不可达死状态**。别为不可达状态操心("栈不空+超上限"逻辑上属 else,但总数锁死使它不可达)。缺可达性分析会凭空制造矛盾。
- **选容器/设计基于当前场景真实需求,警惕从相似场景惯性套用**:GameObject 池要删中间(用List)、纯C#池只两端进出(用Queue)——需求不同选型不同,别把 A 的需求想当然搬给 B。
- **传参别在可能为 null 的对象上提前取成员**(`.transform`):传整个对象,让接收方在自己的保护逻辑里取。
- **★ 约束加"入口"不加"出口"**:限制资源(上限)加在"创建入口",不加"取用出口";出口拦会导致"有资源却不用去抢占",本末倒置。
- **通用方法判断不了调用上下文时,加参数让调用方告知**,别自己猜(ClearPool 判断不了"切场景 vs 手动清"→ 加 `destroyObj` 参数)。
- **过早优化是万恶之源**:无 Profiler 证明是瓶颈前不优化;识别"收益<成本"要**果断撤销**——撤销不是失败,是判断力。

            _usedList.Remove(obj);
        }
        public void PushUsedList(GameObject obj)
        {
            _usedList.Add(obj);
        }
        public void PushStack(GameObject obj) 
        {
            obj.SetActive(false);
            if (isOpenLayout)
                obj.transform.SetParent(_PoolDataRoot.transform);
            _stack.Push(obj);
        }
        public void DestroyAllGameObj() 
        {
            while (_stack.Count > 0) 
                Destroy(_stack.Pop());
            for (int i = 0; i < _usedList.Count; i++)
                Destroy(_usedList[i]);
            _stack.Clear();
            _usedList.Clear();
        }
    }

    private Dictionary<string, PoolData> _poolGameObjDic = new();
    private Dictionary<string, IPoolObject> _PoolObjDic = new();
    private GameObject _poolMgrRoot;
    public GameObject GetObj(string name)
    {
        if (PoolData.isOpenLayout && _poolMgrRoot == null)
            _poolMgrRoot = new("Pool");
        GameObject obj;
        if (!_poolGameObjDic.ContainsKey(name) || (_poolGameObjDic[name].StackCount == 0 && _poolGameObjDic[name].NeedCreate))

        else
            Debug.LogError("传入正确的对象");
    }
    public T GetObj<T>(string nameSpace = "") where T : class, new()
    {
        string key = nameSpace + typeof(T).Name;
        return _PoolObjDic.ContainsKey(key) && (_PoolObjDic[key] as PoolObject<T>).queue.Count != 0 ? (_PoolObjDic[key] as PoolObject<T>).queue.Dequeue() : new T();
    }
    public void PushObj<T>(T obj, string nameSpace = "") where T : class, new()
    {
        string key = nameSpace + typeof(T).Name;
        if (!_PoolObjDic.ContainsKey(key))
            _PoolObjDic.Add(key, new PoolObject<T>());
        (_PoolObjDic[key] as PoolObject<T>).queue.Enqueue(obj);
    }
    public void ClearPool(bool destroyObj , bool isClearObject = false)
    {
        if (destroyObj) 
        {
            if (PoolData.isOpenLayout)
                Destroy(_poolMgrRoot);
            else
                foreach (var key in _poolGameObjDic.Keys)
                    _poolGameObjDic[key].DestroyAllGameObj();
        }
        _poolGameObjDic.Clear();
        _poolMgrRoot = null;
        if (isClearObject)
            _PoolObjDic.Clear();
    }
    public void Warm(string name, int count) 
    {
        if (count <= 0)
            return;
        GameObject obj = GetObj(name);
        PushObj(obj);
        if (_poolGameObjDic[name].MaxNum < count) 
        {
            Debug.LogWarning($"预热数{count}超过对象数量上限{_poolGameObjDic[name].MaxNum}，已经自动截断为{_poolGameObjDic[name].MaxNum}");
            count = _poolGameObjDic[name].MaxNum;
        }
        for (int i = 0; i < count - 1; i++) 
        {
            GameObject gameObj = Instantiate(Resources.Load<GameObject>(name));
            gameObj.name = name;
            _poolGameObjDic[name].PushStack(gameObj);
        }
    }

**那个"脑子里自动出现步骤流"的能力,真名叫什么:**

它不是记忆,是**分解能力(decomposition)**——拿到一个大需求,能把它拆成"要素 → 子步骤 → 顺序"的能力。这个能力**不是背出来的,是练出来的**,而且有具体练法。我今天推你走的那些问题(先做什么、这一步依赖什么、这个之前必须有什么),其实就是**分解的思考动作**。你要学的不是那些步骤的答案,是**那些提问本身**——把我问你的问题,变成你问自己的问题。

### 内存泄漏(memory leak)

术语:**内存泄漏(memory leak)**。这个具体形式叫**事件导致的内存泄漏**,或者更细的名字——**失效监听器 / lapsed listener**(订阅者已经"失效"了,但监听关系还赖着不走)。你说"可能没见过",正常,这是个偏工程经验的词,不是语法点,查一次记住就行,不算缺口。

补一个 Unity 语境下的重点,因为这直接关系你以后写代码会不会踩:

MonoBehaviour(比如 A 是个挂在 GameObject 上的脚本)的情况更阴。你 `Destroy` 了那个 GameObject,Unity 层面它"没了"——但如果某个长命的事件(挂在全局管理器、单例上)还订阅着 A 的方法,**C# 这边的托管对象 A 根本没被回收**,它被订阅列表引用着。结果是:一个你以为已经销毁的对象,事件一触发,它的方法照样被调用,而它内部访问的东西可能已经是残废状态 → 抛异常,或者更糟,悄悄执行了不该执行的逻辑。这就是为什么 Unity 里 `OnEnable` 里 `+=`、`OnDisable`/`OnDestroy` 里 `-=` 是条铁律——成对出现,谁订阅谁负责退订。

你之前学的事件中心 / 消息系统,如果临摹过,里面八成有一套"移除监听"的接口,原因就是这个。

---

顺带点一个 Unity 里的现实后果,不用深挖,先埋个印象:正因为堆对象靠 GC 回收、而 GC 触发时会有开销(可能造成帧率卡顿,俗称"GC 尖峰"),所以 Unity 性能优化里有一大块就是"**减少堆分配、别频繁 new**"——比如别在 Update 里每帧 new 对象。这直接连回你刚问的:每 new 一次堆上开一块,new 得太勤 → 垃圾产生快 → GC 来得勤 → 卡顿。现在只要记住"堆分配有代价、GC 有开销"就够,以后讲优化会回来。
