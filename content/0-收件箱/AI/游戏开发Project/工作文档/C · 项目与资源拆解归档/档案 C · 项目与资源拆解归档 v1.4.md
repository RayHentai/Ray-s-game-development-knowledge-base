#### 复刻检查点(吃透小车的完成标准)

**标准**:关掉教程和参考工程,能从零重建 **2 个核心系统**,并讲清每个关键设计决策的 why。

- **检查点 1 · 程序化网格生成**:合上教程重建顶点生成(sin/cos 圆柱展开)、UV 映射、三角形索引构建。能讲清:为什么顶点 z 乘 π 而 UV 不乘、为什么逆时针绕序(法线朝内)、三角形索引怎么推。
- **检查点 2 · 无限地图拼接**:合上教程重建双缓冲对象池 + 协程替换 + Lerp 首尾衔接。能讲清:为什么只存两块、销毁替补的顺序、beginPoint 的 xy 取上块末尾 / z 取自身的原因、Lerp 过渡的进度机制。

两个都过(能重建 + 讲清 why)→ 小车结项,进孤胆英雄。选这两个而非全部:它们最核心、最能讲、最接近农场"系统级"复杂度;摄像机/UI 等通用模板不纳入(地毯式复刻性价比低)。

**判据提醒**:复刻 = 详细逻辑重建,逻辑正确能跑通即可,命名细节可不同。API 可查,逻辑串不起来才是没吃透。

**来源**:实战 · 小车项目答疑长会话

> **无限地图拼接 · 摸底状态(重现层数据点 · 修订)**
> 
> **架构层(✅ 在)**:双缓冲(最多两块 0/1 循环复用)、地动非车动、触发点(车到后块偏前 / 空对象标记子物体 / 视野穿帮约束)、移除同步接新——均能主动讲出。理解架构态**通过**。
> 
> **坐标衔接(⚠️ 经引导推出,直觉不稳)**:新块起点取值,初次闭卷调不出(明确"不知道"),但经引导**自己推出了核心逻辑**:
> 
> - **xy 取旧块末尾圈** —— 对齐柏林噪声凹凸,防接缝断层。用户能自主讲出目的。
> - **z 接旧块末尾圈 + 一个圈间隔** —— 防重叠 + 续延伸。**此点直觉极不稳**:用户在"z 相等 vs +一个间隔"上反复摔(先"就是旧块z值"→纠→"等于末圈z"→借"首末都有顶点"翻案→最终锁定"末圈+一个间隔")。"接续≠相等,差一个步长"这个直觉顽固易错,列为复刻必练点。
> - **Lerp 首尾衔接** —— 用户原记得"用了 Lerp",本轮补上 why:接缝硬接有急转,故接缝后若干圈从旧块末尾高度渐变到新块本高度。因果这次才通。
> 
> **附带暴露(新)· fencepost**:countZ 语义,用户初认"= 圈数",自纠为"= 间隔数,实际圈数 = countZ+1"。栅栏柱关系,自主纠回。
> 
> **诊断**:架构讲得出、坐标衔接经引导能推出但直觉不稳——比"纯缺口"好,属"结构在、衔接细节的精确直觉在摇摆"。印证根源 1"理解架构≠能稳定复刻":缺的不是架构,是**坐标衔接这类需精确边界处理的细节**,一摸就露、一引导能回、但没到闭卷稳定调出。归复刻检查点 2 必练。
> 
> **来源**:实战 · 全域摸底会话

##### 追加 · 缓存池(对象池)模块复刻记录

**【复刻批次01 · 模块3 · 缓存池 —— 闭卷通过(闭卷+浅迁移)】**

**类型**:程序小框架第3个 · **递进型教材**(4层递进优化,首个递进型,催生档案B"分层递增/全貌关/整体闭卷"等方法论)。

**完成标准三条(对照批次要求)**:

- ①完全闭卷重建:✅ 简版→窗口布局→上限v1/v2→非Mono **五版全闭卷**,且**从零整体闭卷**3版收敛(白纸重建整个模块)。
- ②讲清设计why:✅ 两条GC链、name一名多用、上限约束加入口非出口、两类对象生命周期差异——总测均自主答对。
- ③能评判设计优劣:✅ 全局讨论优化空间 + 反向判断"何时不优化"(线程安全/防重复Push/参数校验均判不做)+ 过早优化撤销——达迁移/评判态。

**四态标(逐层)**:

|层|what|四态|闭卷表现|
|---|---|---|---|
|简版|字典(柜子)+ Stack(抽屉)+ 取/放/清|闭卷|激活/改名2版补齐|
|窗口布局优化|抽屉升PoolData类 + 三层父子(柜根>抽屉根>对象)+ isOpenLayout开关|闭卷|挂父子/惰性创建/空引用3版补齐|
|对象上限v1|usedList记在用 + 抢占最老 + maxNum(GetObj参数)|闭卷|PoolData类一次零错;复合条件短路2版|
|对象上限v2|maxNum改PoolObj脚本配置 + NeedCreate + throw|闭卷|首版即对,漏删死参数|
|非Mono对象|泛型PoolObject<T> + IPoolObject接口 + 里氏替换 + 向下转型|闭卷+浅迁移|短路/Push建抽屉时机2版|
|迁移·预热Warm|提前造N个填闲置栈(入口限数≤maxNum)|浅迁移|**用户自主发现变体**;数量/边界反复滑|
|迁移·ClearPool增强|destroyObj双参数 + 两类池子区别销毁|浅迁移|**用户自主发现幽灵泄漏缺陷**|

**整体判定**:⚠ **达"闭卷+浅迁移"**——四层全闭卷、能整体从零重建、能发现并改变体。**未达深迁移**(改变体时"为什么"仍需引导厘清,尤其两类对象本质差异)。

**what/why/依赖(面试底稿)**:

- **用途**:高频Instantiate/Destroy性能问题——省堆分配+深拷贝(Instantiate侧)、省垃圾不喂GC(Destroy侧)。判据=高频创建销毁。
- **两条GC链(精确)**:Instantiate→堆增长→触发GC(不需Destroy参与);Destroy→制造垃圾→加重GC单次清理。两个独立喂GC,非串联。
- **架构分层**:PoolMgr(管字典/该不该新造)→ PoolData(管一个抽屉的取放)→ 两套字典(GameObject池 vs 纯C#对象池,分而不合)。
- **依赖**:继承不继承Mono单例基类(地基·已闭卷);Resources.Load 加载Prefab。
- **关键设计洞察**:name一名多用(字典键+Resources路径+obj.name校准);上限约束加"入口"(Instantiate阈值+预热限数)非"出口"(有闲置永远优先复用);GameObject可被Unity销毁会悬空 vs 纯C#对象靠引用存活永不悬空(决定两类池能否抢占/是否清)。

**遗留/薄弱(带入后续复刻留意)**:

- **精确执行层**(收尾/簿记动作漏、存在性/短路、时序、模板vs实例混)——**整体闭卷3版全栽执行层、无一在架构层**,与单例轮static、公共Mono复制粘贴改漏同族,证据再+1。
- **两类对象惯性混淆**:GameObject逻辑套纯C#对象(栽5次:Queue/上限/生命周期/Push建抽屉/ClearPool)——第4层核心教训。
- **归因偏**:机制方向对、具体因果链栽(GC由Destroy触发×、class约束因as×)。
- **错别字/术语**(场→厂/Data→Date/冗余→荣誉/出现→出钱)——白板扣分,面试前专项。

**整体判定**:⚠ **达"闭卷+浅迁移"**——四层全闭卷、从零整体重建一次写全、能在已有模块上加新能力(AddOnce)。⚠ 迁移设计阶段经Claude审阅(用户选择),**独立设计判断未测**;未达深迁移。

**what/why/依赖(面试底稿)**:

- **用途**:解耦"一件事发生、多方响应"——发生方不认识响应方,新增响应方不改发生方、不改事件中心。判据=一对多通知。
- **反例**:强关联系统(需要返回值、确定顺序、可追踪调用,如背包↔品质)——事件中心只能"通知",不能"询问"。
- **架构**:发生方 → EventCenter ← 响应方(星形依赖,两端互不认识);容器 `Dictionary<E_EventType, IEventInfo>`,value 是 EventInfo / EventInfo<T>,里面装 UnityAction / UnityAction<T> 多播委托。
- **依赖**:不继承Mono单例基类(纯逻辑,不需生命周期·地基已闭卷);UnityEngine.Events.UnityAction。
- **关键设计洞察**:存和调是两件事(注册只存,发生方显式Trigger才调);一个事件一种签名(约束非缺陷;零参数也是一种签名→非泛型重载存在的意义);转换从数据层(object→int,装箱)挪到容器层(IEventInfo→EventInfo<T>,引用转引用);名字错→编译期(enum),类型错→运行时(throw);删空保留key(enum上限小,省反复new);传专门的数据载体、不传发生方(小而不可变用struct,零GC);过场景不调全局Clear()(误伤常驻监听)——危险API不提供。
- **完整代价**:enum单点热点+模块不能单独复用;注销责任全在使用方;类型契约只能运行时查;全局清理误伤;出错多为静默;单向无返回值;隐式调用链、执行顺序不保证。
- **教材疑点**:"委托的坑(直接Add就无法移除)"不存在(null+=func返回func本身;委托相等比目标+方法),真正的坑是lambda;"过场景调Clear()"会误伤常驻监听。

**遗留/薄弱(带入后续复刻留意)**:

- **精确执行层**:复制粘贴改漏(第4次,⑥首次受检验通过)、对称遗漏、**方向/角色表述精度**(新子类)、**审题/答题完整性**(新子类·双因)——与对象池/公共Mono同族,证据再+1。
- **两类对象复发**:Destroy只毁引擎层、C#壳被委托抓着、MissingRef——⑧没调出。
- **由头推导每层都要钩子**;遇数据形状不合倾向拆事件(两信号)。
- 表述小项:讲enum/泛型的设计收益时,主动说出"编译期就能发现"。

**新增正向(见档案A)**:"存/调分离"从空缺走到掌握;合理异议多次被采纳;主导建立/校准多条规则;首次自主关联公共Mono。

**待复习闭卷自测点(进Obsidian §8)**:存/调分离;监听方Destroy没Remove为何还执行+三种后果;为什么不能写EventCenter<T>;转换发生在哪一层、会不会装箱;两类错误分别在哪拦;删空留不留key;事件该传什么、struct还是class;过场景要不要Clear;lambda注销陷阱;什么时候不该用事件中心。
