# 档案 D · 复盘归档 v1.0

## 档案 D · 场景01 · 首次全域摸底(理解层+重现层闭卷)

**场景**:人生第一次闭卷检验。理解层口头摸底(小车核心)+ 重现层闭卷(从零写圆柱隧道 mesh)。

**实际反应**:
①理解层——多数概念初答带一个错位(顶点空间/triangles存啥/绕序现象/sharedMesh),但一经追问即自恢复或诚实认不知;架构层(无限拼接)主动讲出、完整。
②重现层——顶点生成顺(自恢复快);triangles 卡很久,尤其"四角偏移右下vs左上"绕五轮,反复用"换一组写死数字""起点不同""顺逆时针"回避正面确认偏移公式,最终靠"看z坐标"钉死才通。
③自主动作——绕序自己看效果反、闭合自己确认、countX/countZ手误自己会在提示后改。

**诊断(卡在理解链条哪环)**:卡在 **"符号-空间映射"环**——不是不懂原理(sin/cos会推、三角形拼法会),是"数组索引 ↔ 空间位置"的对应在脑中无稳定模型,triangles 偏移全靠现推,故易错、易在追问下动摇。理解层"结构在标签松"(一戳回),重现层"边界精确性"最薄(fencepost 3次、偏移5轮)。

**目标反应**:偏移公式应能凭"同圈+1/跨圈+每圈点数"的空间含义直接写出,不需五轮试错;fencepost 应形成"桩vs段"条件反射。

**启发**:
①摸底证实根源1判断准确(架构≠复刻,缺口在细节层不在理解端)。
②新增精确定位:重现缺口不是笼统"不会复刻",是特指 **"索引/坐标边界精确性"** 这一薄弱层——下阶段练习应针对性打这个,不需重练顶点/架构。
③回避模式在闭卷中有新表现:卡壳时倾向"换个能跑的具体解"绕过"正面确认抽象公式",需被拦住逼其面对。

**来源**:实战 · 全域摸底会话

**档案D · 场景01 附注 · 本次摸底覆盖边界**:实际只覆盖档一中小车项目相关机制(mesh/绕序/sin-cos/无限拼接)+闭卷。档一通用基础未测(C#语言特性/Unity通用/UI,清单见开头)。理解层地图仅代表小车机制,非档一全貌。**待办:C#/Unity通用基础单开一轮理解层摸底。**

**知识点:委托与事件 —— 理解层判定:结构在,一戳全恢复。**

- 初答自评"基本忘了",实际:委托定义准(存方法的类型 / `.Invoke()` / `?.Invoke()` 空安全)、Action/Func 轴一提就接住(返回值为轴,泛型上限 16/16 记得牢)、event 外部限制结论**完全正确**(外部只能 `+=`/`-=`,不能 `=`、不能 Invoke;委托无此限制)、内存泄漏机制能自主推出(订阅列表持有引用 → GC 判定有引用 → 回收不掉)。
- 模式与一轮一致:非塌方,是**生疏 + 边界细节松**。松的具体点:①`=` vs `+=`(在字段式事件内部其实可 `=`,详见下);②裸调 null 委托会 NRE(已会 `?.Invoke()`,属习惯非缺口)。
- 净赚细节:经纠错后掌握"字段式事件在声明类内部 = 私有委托字段本身,故内部可 `=`/可调用"。
- 术语补充(非缺口,查一次即可):事件导致的内存泄漏 / lapsed listener(失效监听器)。Unity 语境:MonoBehaviour 被 Destroy 但长命事件仍订阅 → 托管对象不回收 → 触发时访问残废状态。对应铁律:`OnEnable` 里 `+=` / `OnDisable`/`OnDestroy` 里 `-=` 成对。

**知识点:Prefab/实例化/Variant —— 理解层判定:核心理解到位,1个真误区(runtime同步)+1个概念混淆(SO)。**

- 动态生成必要性:理解到位("运动伴随新对象生成,不可能提前全摆完")。

- 概念混淆:用户以为ScriptableObject能做"加受击闪红"。澄清SO=纯数据不进场景、做不了运行时行为;加行为改Prefab、改数值用SO、二者配合非替代。列Obsidian。

**【档案 D · 场景 02 · Unity组第5点 · Time.deltaTime（含方法论插曲与 Claude 自身错误）· 完整版】**

═══ A. 知识点诊断:Time.deltaTime ═══

理解层判定:主干理解到位(用物理直觉抓对本质),1个真误区(½at²的累计t误当帧间隔Δt),经用户自己的实测纠正。

- 主干:deltaTime是什么(帧间隔时间,"当前一帧所需时间",钉准为两帧间隔)、为什么乘(用"距离公式里的时间"这个物理直觉自主抓对——speed是每秒量、乘Δt换算成每帧量),均理解到位。
- 精度补正:用户说"不乘会不正常地快",方向对但说轻——真问题非"快",是"快慢取决于帧率、跨机器不一致"(60/144/30帧速度全不同、联机不同步)。已讲透"帧率高Δt小、低Δt大,一乘一除→每秒位移恒定=speed"。
- 真误区(非生疏):匀加速运动,用户在Update里写成 position += forward*Δt*Δt(以为加速=Δt平方)。根子=把½at²里的"累计总时间t"错当成"一帧的Δt"。
- 关键(正面):用户诚实说"不知道",并主动给出Unity实测结果("按平方写了,是匀速")。此实测恰成推翻错误直觉的证据(Δt每帧常数→Δt²常数→每帧加固定量=匀速)。经拆解已纠正:加速靠速度变量自累积(speed+=a·Δt),Δt只乘一次;½at²是总量解析公式非逐帧写法。此"不确定就去Unity实测"是用户本人在摸底当场做的动作(与后文'朋友代笔'插曲无关),属根源3反面(主动验证、非回避),好信号。
- 错误归类:属"解析式↔逐帧递推"的语义没对齐(解析公式描述总量、逐帧代码累加增量,两者t同名不同义)。一经拆解即通,轻于弧度/坐标衔接。因涉及"逐帧累加"这一游戏编程核心心智,列入待强化,复刻循环类逻辑时留意。

模式:主干与Unity前四点一致(结构在、理解到位);误区性质同Prefab的runtime同步误区(把某语境的直觉误推到另一语境),非无根缺口。

**【档案 D · 场景 02 · 追加(UGUI 组·第 1 点)】**

知识点:Canvas 渲染模式(Overlay / Camera / World Space)—— 理解层判定:名字全记得、机制生疏,经实测 + 引导即回,非缺口。与 C# 组、Unity 组同型。

- **三模式名字**:全部答对(覆盖/摄像机/世界空间),骨架在。但初答只给名字未给功能差别,故先挖机制。
- **Overlay vs Camera**:用户**自己去 Unity 实测**(好信号,根源 3 反面),观察准确——Overlay UI 永在最前不受 z 影响;Camera 绑 Main Camera 后 UI 被 z 更小的 Cube 挡住。机制经引导讲对:Camera 模式交给 Render Camera 渲染,摄像机看到什么样就渲成什么样,故会被挡。**自主补出准确适用场景**:背包里显示 3D 人物/物体模型。
- **补精度两点**(用户接住):①"为什么被挡"钉死——Camera 模式下 Canvas 被摆进 3D 空间成为与 Cube 平级的 3D 对象、一起进渲染一起比 z,不是"顺便被渲";②带出 Overlay 干不了的能力——UI 与 3D 物体在 z 上交错叠放(粒子穿插 UI 等)。
- **World Space · 校正点(值得记)**:用户初答"VR/AR 专用"——**框窄了**。校正为:World Space = UI 本身是放进 3D 世界的普通物体(有世界坐标/旋转/远近透视),"凡 UI 要待在 3D 世界里、有空间位置和远近就用它",VR 只是其中一种场景。用户经引导能推出"可交互 3D 投影 UI",但给的是偏科幻的抽象描述;拽回日常例子(敌人头顶血条/名字、飘的伤害数字、NPC 感叹号、"按 F 拾取"提示)后落地。**面试风险**:"专用"会把这个概念答窄。

模式:与 C#/Unity 组一致——结构在(名字+骨架)、生疏(平时只用 Overlay,另两个糊了)、一实测/一引导即回。非硬缺口。World Space 的"专用→通用"是本点唯一需校正的实质点,属认知框窄非机制缺失,一经拽回即通。

一句话锚(给用户,以后从例子推非背表):三模式差在"UI 画在哪个空间"——Overlay = 3D 全渲完后单独糊屏幕上(最常用、不比 z);Camera = 塞进 3D 场景交指定摄像机、和物体比 z(UI 里显示 3D 模型时用);World Space = UI 本身是 3D 世界的物体、有远近透视(血条/伤害数字/世界提示牌)。

**错点卡(1 条)**:World Space Canvas 答"VR/AR 专用" → 正:凡 UI 要待在 3D 世界里、有空间位置和远近就用它(血条/伤害数字/提示牌都是),VR 只是其一。

**【档案 D · 场景 02 · 追加(UGUI 组·第 3 点)】**

知识点:CanvasScaler —— 理解层判定:机制初始空(自评只会设置、原理说不清),搭骨架后核心分工能接,但**两个"想当然"错点**。归需练点(轻于硬缺口)。

- **初始状态**:诚实划线——会设(Scale With Screen Size + 填 1920×1080),原理说不清。"手法记得、机制空",同 Canvas 初始态。
- **参考分辨率误解(补正)**:用户把 1920×1080 当"目标分辨率"。纠正:是**参考分辨率(设计基准)**,真机不同时 CanvasScaler 从基准整体缩放过去。
- **核心分工(经引导自主收敛)**:用户自己说出"锚点管相对位置、大小不归它管、CanvasScaler 管大小"——分工抓对。补精确:CanvasScaler 是**整个 Canvas 的 UI 随屏幕整体等比缩放**(尺寸/字号/间距),不是单个元素各自适配。三模式(Constant Pixel Size / Scale With Screen Size / Constant Physical Size)搭骨架后接住。
- **想当然错点 1(Match 方向映射背反)**:用户答"Match=0 竖屏游戏、1 横屏游戏"——反了。0 锁宽(偏横屏,UI 横向铺开怕宽被切)、1 锁高(偏竖屏)。已纠,且提醒别背横竖映射、记"Match 锁的是那方向的合适度",多数折中 0.5。
- **想当然错点 2(黑边归错层)**:用户答"比例不对会出现黑边"——错。CanvasScaler 只做整体缩放+按 Match 让某方向溢出/留白,不加黑边;黑边是摄像机强制画面比例(Aspect Ratio)的产物,属渲染层。用户把 UI 缩放层和摄像机渲染层混了。

模式:比 anchor/pivot 糊(那两点讲对+补细节,这点讲不出+搭骨架+纠两错)。但一搭骨架即接住、非推不动,属**生疏+想当然**,非机制塌方。归需练点,与点乘叉乘选型映射同档(轻于弧度/坐标衔接)。**Match 方向映射是本点最该进 §8 闭卷自测逼复习的**(背反了,需从机制重推固化)。

**【档案 D · 场景 02 · 追加(UGUI 组·第 4 点)】**

知识点:EventSystem 与 UI 事件绑定 —— 理解层判定:"怎么绑"活的(项目做过),"底层派发"初始空但经"3D 射线"钩子迁移推对大方向,搭骨架后全接住。同型,非硬缺口。

- **绑定 API(活的)**:代码路径讲对(声明控件引用→关联→`onClick.AddListener`);拖动绑在 On Click() 用得少、不熟(如实说)。
- **底层派发(初始空→迁移推对)**:问"点击到 onClick 触发中间 EventSystem 做了什么",初始没往底层想。给"3D 射线检测"钩子后,用户**主动迁移**推出"打射线判断打中哪个 UI"——大方向对。
- **核心纠正(值得记)**:用户把 3D 那套**原样搬**——说"判断射线打到哪个 UI 的碰撞箱"。纠正:**UI 射线不用 Collider**,靠 **Graphic Raycaster**(挂 Canvas)遍历 UI 的 RectTransform 矩形+层级算最上层命中;UI 元素身上没 Collider,与 3D 物理射线是两套并行系统。
- **完整链搭骨架后接住**:EventSystem(总调度:监听输入+派发)→ Graphic Raycaster(判断点中谁)→ 派发给命中 UI 触发 onClick。删 EventSystem = UI 全部失效(高频坑)。
- **Raycast Target 吃点击(自主推对)**:验证题(背景 Image 挡住上层按钮点击),用户直接说出"Image 最上层且 Raycast Target 勾选"两个条件——机制真接住。补性能延伸(纯展示 UI 关 Raycast Target 减少遍历)。

模式:同型。**net 信号(重要)**:用户从 3D 射线主动迁移到 UI 射线(细节要拧但大方向自发关联)——这是本轮第 N 次跨机制自主联想(序列化→执行顺序、Transform→父缩放、3D 射线→UI 射线)。**与用户自评"无法关联到新场景"相矛盾**,其关联能力(尤其有共同底层机制的迁移)可能被自己低估。总回传要带给主框。
